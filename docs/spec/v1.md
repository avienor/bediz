# Bediz V1 Specification

## 1. Purpose

Bediz is an open-source deterministic CLI through which a creative AI agent and a human use the same local InvokeAI installation. The agent interprets creative intent and chooses prompts and settings. Bediz validates those explicit choices, compiles supported operations into InvokeAI execution graphs, submits them through InvokeAI's API, and returns stable machine-readable results. The human can observe queue activity and outputs in InvokeAI's web interface and continue the work there.

Bediz does not call an LLM, make creative decisions, reproduce browser gestures, or fork InvokeAI.

## 2. V1 outcomes

V1 provides:

- Basic text-to-image generation for Anima, SDXL, and FLUX.1.
- Tiled generative upscale for SD1.5 and SDXL.
- Prompt, model, image-size, generation-setting, output-count, seed, and board control where applicable.
- Queue submission, inspection, waiting, cancellation, and explicit clearing.
- Gallery image inspection, upload, download, and explicit deletion.
- Model inspection, installation, status, local scanning, and explicit deletion.
- Model sources from InvokeAI starter models, Hugging Face, direct URLs, local paths, and strict Civitai URL resolution.
- Board inspection and creation.
- Local technical generation profiles.
- Version, schema, component, and capability diagnostics.
- Parameter Recall and operation-specific UI synchronization levels.
- A canonical agent skill.

V1 does not provide Canvas brush or layer control, arbitrary workflow authoring, img2img, inpainting, LoRAs, reference images, ControlNet generation, external hosted generation models, video generation, a daemon, a local audit database, a public graph dry-run command, or a general browser-automation layer.

## 3. Product boundary

### 3.1 Creative agent

The creative agent understands the user's intent, improves prompts, selects installed models, chooses technical settings, and decides which explicit Bediz operations to request. It preserves every model, prompt, and setting the user fixes explicitly.

### 3.2 Bediz controller

Bediz performs deterministic validation, model and component resolution, graph compilation, InvokeAI API calls, polling, result normalization, and UI Recall. It never invents creative content or silently changes an unsupported setting.

### 3.3 InvokeAI

InvokeAI remains the execution engine and the source of truth for models, queues, boards, images, metadata, and results. Bediz stores no duplicate job database or audit history.

## 4. Architecture

Bediz is a standalone Go application distributed as a single binary. Its internal typed operation layer is independent from the CLI parser. CLI flags and JSON request documents compile to the same operation types.

The controller uses HTTP APIs and polling in V1. Socket.IO support may be added later. Graph-producing operations use versioned family adapters and a pure, testable graph compiler. The live OpenAPI document validates endpoint and invocation vocabulary, but family-specific graph topology remains Bediz's responsibility.

Browser automation is not part of the normal control path. Bediz runs no daemon and requires no Python environment.

## 5. InvokeAI compatibility

The initial supported range is:

```text
>= 6.14.1, < 6.15.0
```

InvokeAI 6.14.1 is the baseline integration-test version. Later 6.14 patch releases must pass live compatibility checks. A new minor or major version is unsupported until the capability matrix is updated.

Read-only inspection and `doctor` may operate on an untested version when their endpoints are compatible. Graph-producing operations fail with `unsupported_capability`. V1 has no `--allow-untested` override.

The capability matrix records implemented and tested support by InvokeAI version, operation, model family, setting, and UI synchronization level. Planned V1 operations are not registered or reported as compatible until their implementation and compatibility fixtures exist.

## 6. Command surface

```text
bediz version
bediz doctor

bediz generate
bediz recall
bediz upscale

bediz images list|get|upload|download|delete
bediz models list|install|status|scan|delete
bediz queue list|get|wait|cancel|clear
bediz boards list|get|create
bediz profiles list|get|create|delete
bediz config get|set

bediz auth huggingface status
bediz auth huggingface login --token-stdin
bediz auth huggingface logout
```

Commands default to concise human-readable output. `--json` selects the stable machine contract. Colors are disabled when output is non-interactive.

## 7. Connection and configuration

Connection values resolve in this order:

1. `--url` and `--token`
2. `BEDIZ_URL` and `BEDIZ_TOKEN`
3. Per-user Bediz configuration
4. `http://127.0.0.1:9090`

V1 has one active target and no named target profiles. The primary deployment is Bediz and InvokeAI on the same machine. Single-user InvokeAI requires no token. Tokens are never logged.

## 8. Request contract

### 8.1 Canonical representation

Each operation has a typed JSON request document with required `schema_version: 1`. A request may be read from a file or standard input:

```text
bediz generate --request request.json
bediz generate --request -
```

Common operation flags are a convenience representation of the same request. Operation-field flags cannot be combined with `--request`. Connection, output, wait, and timeout flags may accompany it because they do not alter operation semantics.

Unknown request fields are validation errors. Bediz does not ignore misspelled or inapplicable settings.

### 8.2 Exact selectors

Installed models are selected by InvokeAI model key. Model and board names are accepted only when they resolve uniquely. Ambiguity returns `selection_required` with structured candidates; no interactive terminal picker is used.

### 8.3 Defaults

Generation values resolve in this order:

1. Model-family defaults
2. Named generation profile
3. Explicit request values

The creative agent selects the main model unless a profile or user constraint already identifies it. Bediz may resolve required auxiliary components under the component-resolution rules.

## 9. Result and error contract

With `--json`, standard output contains exactly one final JSON object:

```json
{
  "schema_version": 1,
  "ok": true,
  "operation": "generate",
  "data": {},
  "warnings": []
}
```

Errors use the same envelope with a structured `error` containing a stable code, message, and relevant details. Progress and diagnostics never contaminate JSON standard output; necessary operational messages use standard error.

V1 does not provide JSON Lines progress events. A caller may use `--no-wait` and later call `queue get` or `queue wait`.

Process exit statuses are:

- `0`: success
- `2`: invalid request
- `3`: selection required
- `4`: incompatible or unsupported capability
- `5`: connection or authentication failure
- `6`: InvokeAI operation failure
- `130`: interrupted locally

## 10. Diagnostics

`bediz doctor` is a readiness check, not a connectivity ping. It reports:

- Bediz and InvokeAI versions.
- Connection and authentication status.
- OpenAPI availability and the endpoints required by registered capabilities.
- Invocation types and fields required by registered capabilities.
- Installed main and component models relevant to registered capabilities.
- Capability-matrix matches and failures.
- UI synchronization levels for registered operations that support synchronization.

A planned operation is absent from the report until its delivery slice implements and tests it. Anima Direct Execution requirements are advertised after the end-to-end generation slice; UI Synchronization is advertised after its own implementation and compatibility fixtures are verified.

Recall readiness is reported separately from Anima Direct Execution readiness. A missing Recall endpoint or an incompatible Recall patch schema fails the `recall` capability with the missing requirement named; it does not make a compatible `generate` capability incompatible. `ui_sync.generate` is `partial` only when the supported version, Direct Execution, and tested Recall requirements are all compatible. It is omitted when those requirements are not met.

After the corresponding operation slices are implemented and registered, V1 synchronization status on stock InvokeAI 6.14.x is:

```json
{
  "ui_sync": {
    "generate": "partial",
    "upscale": "partial"
  }
}
```

## 11. Text-to-image generation

### 11.1 Supported families

- Anima
- SDXL
- FLUX.1

The first end-to-end implementation slice targets Anima. SDXL and FLUX.1 follow as separate tested graph adapters.

### 11.2 Core fields

A generation request supports, where applicable:

- Exact main-model key
- Positive prompt and optional negative prompt
- Width and height
- Steps
- Scheduler
- Guidance or CFG scale
- Seed
- Output count
- Output board identifier
- Supported explicit component overrides

Width and height are supplied together or both resolve from a profile or family default. Bediz validates family bounds and alignment. Aspect-ratio presets are not part of the canonical V1 request.

Steps, scheduler, guidance, CFG, and negative prompts are typed, family-aware settings. Supplying a field whose semantics are unsupported for the selected family is an error.

V1 exposes no arbitrary `--advanced key=value` escape hatch.

The schema-version-1 Generation Request uses these canonical JSON field names:

- `schema_version`
- `model`
- `positive_prompt`
- `negative_prompt`
- `width` and `height`
- `steps`
- `scheduler`
- `guidance`
- `seed`
- `output_count`
- `board_id`
- `components`, containing the typed `vae` and `qwen3_encoder` selectors for Anima

The matching convenience flags are `--model`, `--prompt`, `--negative-prompt`,
`--width`, `--height`, `--steps`, `--scheduler`, `--guidance`, `--seed`,
`--output-count`, `--board`, `--vae`, and `--qwen3-encoder`.

For Anima, omission resolves without consulting browser state: the negative
prompt becomes empty, dimensions become 1024 by 1024, steps become 30, the
scheduler becomes `euler`, guidance becomes 4.5, and output count becomes one.
Explicit request values override these family defaults. Width and height must
be supplied together and resolve to positive multiples of 8; steps and output
count must be positive; guidance must be finite and at least 1; and a seed must
be an unsigned 32-bit integer. The supported Anima schedulers are `euler`,
`heun`, `dpmpp_2m`, `dpmpp_2m_sde`, `er_sde`, and `lcm`. The Anima capability
accepts any positive output count. InvokeAI queue-capacity rejection remains a
conclusive operation failure rather than a Bediz-specific arbitrary maximum.

### 11.3 Seeds and multiple outputs

When the request omits a seed, Bediz assigns a valid random seed to each output before submission. When it supplies a seed for multiple outputs, the first output uses that seed and later outputs increment it sequentially within the family's valid range. Every resolved seed appears in the execution receipt.

### 11.4 Component resolution

Bediz queries installed model inventory for family-required auxiliary components:

- An explicit request override wins.
- A profile preference is used when compatible.
- One compatible installed component is selected automatically.
- Multiple compatible candidates return `selection_required`.
- No compatible component returns a structured missing-component error with install guidance when known.

Bediz never chooses the first arbitrary installed model.

The Anima main-model selector resolves only to an installed model with base
`anima` and type `main`. The first tested Anima component combination is a VAE
with base `anima` and type `vae` plus an encoder with base `any` and type
`qwen3_encoder`. An explicit compatible key or unique name wins; without a
selector, exactly one compatible installed component is selected. Ambiguous
names or several automatic candidates return `selection_required` (exit status
3) with candidates sorted by Model Key. An absent automatic component returns
`missing_component` (exit status 4) with its component type, required base and
type, and installation guidance. The OpenAPI-described FLUX VAE fallback and
Generation Profile preferences remain unsupported until their tested slices.

### 11.5 Submission and completion

`generate` compiles an execution graph and submits it to InvokeAI's default queue. It waits for completion by default. `--no-wait` returns accepted queue identifiers.

For Anima on InvokeAI 6.14.x, the tested graph contains one
`anima_model_loader`, one positive `string` input, positive and negative
`anima_text_encoder` nodes with their `collect` nodes, one `integer` seed,
one `anima_denoise`, one `core_metadata`, and one `anima_l2i` output node.
Typed edges carry the loaded transformer, Qwen3 encoder, VAE, prompt
conditioning, seed, denoised latents, and metadata to their consumers. Model
inputs use complete InvokeAI Model Identifiers. The denoise and metadata nodes
contain the resolved dimensions, steps, scheduler, guidance, negative prompt,
model, VAE, and Qwen3 encoder, while edges carry the positive prompt and seed
into metadata. Node identifiers may vary without changing this contract.

One logical generation is submitted in one `enqueue_batch` mutation to the
`default` queue. Bediz never automatically retries that mutation. Before that
mutation, Bediz resolves the complete ordered seed set and compiles one
InvokeAI batch that produces one queue item per seed. For InvokeAI 6.14.x, the
adapter orders the batch seed values so the returned `item_ids` and
`resolved_settings.seeds` describe the same outputs at the same positions.

Waiting polls read-only queue inspection for each accepted item, preserving the
enqueue response order, until every item reaches a terminal state. Polling
never replays the enqueue mutation and never calls a cancellation endpoint.
InvokeAI 6.14 queue items use `pending`, `in_progress`,
`waiting`, `completed`, `failed`, and `canceled`; the first three are
non-terminal, where `waiting` means the item is suspended while a workflow-call
child item runs. A status outside this tested set fails with
`invalid_invokeai_response` instead of being treated as terminal or polled
indefinitely. Waiting has no total timeout; when supplied, `--timeout` bounds
only the local wait while every HTTP request keeps its own bounded transport
timeout. An elapsed wait deadline returns `wait_timeout` with the accepted queue
identifiers, and local interruption returns `interrupted` with the same
identifiers.

Interrupting a waiting Bediz process or reaching a local wait deadline does not
cancel the InvokeAI item. Cancellation is a separate `queue cancel` operation.

### 11.6 Execution receipt

A completed request returns:

- The submitted request
- Fully resolved settings
- Exact main and component model keys
- Queue batch and item identifiers
- Per-output seeds
- Image references and InvokeAI URLs
- Output board
- UI synchronization warnings

Generated images remain in InvokeAI. Local download is an explicit `images download` operation.

The schema-version-1 Execution Receipt uses these fields:

- `submitted_request`: the canonical Generation Request before defaults or automatic component resolution.
- `resolved_settings`: the resolved prompts, dimensions, steps, scheduler,
  guidance, output count, optional board identifier, exact `model_key`, typed
  `component_keys`, and ordered `seeds`.
- `queue`: the `queue_id`, `batch_id`, and ordered `item_ids` returned by InvokeAI.
- `outputs`: ordered item, seed, and Image Reference associations; this is an
  empty array in an accepted `--no-wait` receipt.
- `warnings`: UI synchronization warnings, also present in the Result Envelope.

A completed item yields exactly one output record per queue item: the item
identifier, the resolved seed at the same position in `resolved_settings.seeds`,
and the normalized Image Reference with its absolute InvokeAI image and
thumbnail URLs. Bediz verifies that same-position association against each
queue item's recorded batch seed. Missing or contradictory seed metadata, or a
completed item that exposes no image output or more than one, fails with
`invalid_invokeai_response` instead of a guessed association. If any item in a
batch fails or is canceled, the generation fails with
`invokeai_operation_failed`, the accepted queue identifiers, and a concise
normalized message; a partially completed batch is never reported as a
successful receipt, and server tracebacks are never exposed.

## 12. Parameter Recall and UI synchronization

`bediz recall` submits a supported generation parameter patch to InvokeAI's Recall API without enqueueing generation. On stock InvokeAI 6.14.1, the Anima patch fields consumed by the frontend are the positive and negative prompts, exact main model, width and height together, steps, and seed. At least one supported field is required. Prompts and seed may be patched without a model; dimensions and steps require an explicit Anima model so Bediz can validate their family-specific meaning. A schema-version-1 Recall Request Document and the matching convenience flags compile to the same typed operation. Unknown or inapplicable fields are errors.

The Recall Request Document contains `schema_version` and the optional `model`, `positive_prompt`, `negative_prompt`, `width`, `height`, `steps`, and `seed` fields. The corresponding flags are `--model`, `--prompt`, `--negative-prompt`, `--width`, `--height`, `--steps`, and `--seed`. Operation flags cannot be mixed with `--request`. The shared fields use the Anima Generation Request constraints, except that stock InvokeAI 6.14.1's Recall API requires both dimensions to be at least 64 pixels. Bediz rejects smaller Recall dimensions before posting. Successful machine output is one V1 Result Envelope with `operation: "recall"`, empty warnings, and data containing `queue_id: "default"` and `mode: "patch"`. Success means InvokeAI accepted the patch; it does not assert that a browser was open to receive the event. An inconclusive Recall mutation returns `outcome_unknown` without a retry.

InvokeAI 6.14.1 resolves the Recall main model by display name and takes the first match. Bediz resolves the requested Model Key or unique name before Recall and submits its display name only when that name identifies the same single installed main model. An ambiguous input selector returns `selection_required`; a selected key whose display name collides with another main model returns `unsupported_capability`. Both fail before mutation. V1 does not offer `recall --replace`: the stock 6.14.1 frontend ignores the null scalar values sent by InvokeAI's strict Recall mode, so omitted scalar controls remain populated.

After a successful generation enqueue, Bediz attempts to patch the supported resolved fields by default, using the first output's resolved seed when there are multiple outputs. It does not retry the Recall mutation. Generation remains successful if Recall fails or exact model Recall is impossible; the result contains a structured `ui_sync_failed` warning. A successful partial synchronization carries a `ui_sync_partial` warning identifying the generation fields that the stock frontend cannot restore. The Execution Receipt always retains every resolved setting and output seed.

On stock InvokeAI 6.14.x:

- Anima generation synchronization is partial. The frontend Recall event handler maps prompts, model, dimensions, steps, and seed to UI state, but does not restore Anima scheduler, guidance, VAE, Qwen3 encoder, output count, or Output Board controls. The visible queue item, result image, metadata, and Execution Receipt remain available for Handoff.
- Generative upscale synchronization is partial.

Partial upscale synchronization guarantees visible queue items, result images, embedded metadata, prompt and seed recall where supported, and an exact Bediz execution receipt. It does not repopulate the source image, Spandrel model, scale, creativity, structure, Tile ControlNet, tile size, or tile overlap in the Upscale panel.

Bediz will not manipulate browser storage or DOM state to simulate missing Recall fields. A later InvokeAI version may upgrade generation or upscale synchronization to full only after its API and frontend behavior have been tested. Live UI verification uses a browser to observe the Handoff result; the browser is not part of Bediz's control path.

## 13. Generative upscale

V1 `upscale` implements InvokeAI's tiled multi-diffusion upscale, not a standalone RealESRGAN resize.

Supported main-model families:

- SD1.5
- SDXL

The operation resolves:

- Main model
- Spandrel image-to-image upscale model
- Compatible Tile ControlNet
- Optional VAE

The request may include positive and negative prompts, scale, creativity, structure, steps, scheduler, CFG scale, seed, tile size, tile overlap, optional VAE, and output board. LoRAs and additional post-processing models are deferred.

The source is either an existing InvokeAI image name or an absolute local image path. A local file is uploaded first, and the resulting image reference is recorded in the receipt. If graph submission later fails, Bediz reports the uploaded source and does not delete it automatically.

## 14. Model management

Supported install sources are:

- InvokeAI starter model identifier
- Hugging Face reference
- Direct URL
- Local server path
- Civitai model-version page or identifier resolved to a direct artifact

The implemented URL slice accepts `models install --source-type url --source URL` or a Request Document such as `{"schema_version":1,"source":{"type":"url","reference":"https://example.org/model.safetensors"}}`. It rejects userinfo, any query, and any fragment before mutation, and does not mix operation flags with `--request`. A successful install returns `{"jobs":[{"job_id":0,"status":"waiting","source_type":"url","role":"requested"}]}` in the V1 Result Envelope's `data`; the actual job ID and status come from InvokeAI. It submits through the generic POST install endpoint exactly once. If the response is inconclusive, `outcome_unknown` directs callers to inspect the current model inventory and install job list before another submission.

`models status --job-id 0` and `{"schema_version":1,"job_id":0}` inspect the job currently held under that non-negative ID. The `data` projection contains `job_id`, normalized `status`, optional `bytes` and `total_bytes`, and `model_key` only when a completed backend record supplies one. Unknown statuses return `invalid_invokeai_response`; absent jobs return `not_found`. The projection excludes backend source, credentials, error text, and traceback. IDs can disappear or be reused after an InvokeAI restart, so status does not establish a durable installation identity. `doctor` registers installation only when the tested generic POST endpoint advertises a required `source` query parameter and a JSON `201` response containing a `ModelInstallJob`; it registers status as compatible read-only inspection.

An Installation Request Document requires `schema_version: 1` and a `source` with typed `type` (`starter`, `huggingface`, `url`, `path`, or `civitai`) and `reference`. Matching source flags compile to the same operation. An exact Civitai file may additionally use a positive integer `source.file_id`; a server path may use the operation's `move` setting. Unknown and inapplicable fields are errors. The install result returns accepted job identifiers, statuses, source types, and roles without echoing source references. `models status` takes an exact non-negative integer job ID (including zero) and returns an allowlisted job state, with an installed Model Key only when verified from a completed job. InvokeAI 6.14.1 scopes these IDs to its current install-job registry: after a server restart, an ID can disappear or identify a different job. Bediz does not treat an old ID as a durable installation receipt; callers inspect the current model inventory and job list before acting on an uncertain outcome. Raw backend source, token, error text, and traceback are not returned.

The tested InvokeAI install states are `waiting`, `downloading`, `downloads_done`, `running`, `paused`, `completed`, `error`, and `cancelled`. A status outside that set fails as `invalid_invokeai_response`; Bediz does not guess whether the job finished. A job no longer retained by InvokeAI returns `not_found`, not an inferred success.

Starter-model dependencies declared in InvokeAI's returned catalog are submitted in catalog order before the selected starter as separately observable jobs. A starter is selected by its exact `source` identifier, not by a potentially duplicated display name. The starter result has `jobs` and `skipped` arrays. Jobs contain the accepted `job_id`, normalized `status`, `source_type: starter`, `role` (`dependency` or `starter`), and zero-based `dependency_index` for a dependency. Entries present in the catalog and marked installed are reported in `skipped` with the same role and index and `reason: already_installed`, before source normalization; unsupported installed source forms do not block the request. If every returned entry is installed, `jobs` is empty. InvokeAI 6.14.1 omits installed dependencies from the returned dependency list, so Bediz cannot identify or report those omitted entries; dependency indexes refer to the returned list. Bediz preflights every entry it would install and returns `unsupported_capability` before any mutation if a source form or required protected-repository authentication input is unsupported. A single `--token-stdin` value is sent only when all entries to install have the same URL origin; a mixed-origin starter request with a source token fails as `unsupported_capability` before mutation. A partial rejected submission returns `invokeai_operation_failed` with accepted `jobs`, `skipped`, the rejected role/index, and HTTP status when available. An inconclusive submission returns `outcome_unknown` with accepted `jobs`, `skipped`, and the uncertain role/index. Neither is replayed automatically; a concurrent 409 is a conclusive conflict requiring reinspection. Bediz does not guess dependencies for arbitrary Hugging Face, URL, path, or Civitai artifacts; `doctor` reports missing required components and advertises starter installation separately only when the tested catalog and generic job endpoints are present.

The implemented Hugging Face slice accepts `models install --source-type huggingface --source org/repo` or the matching schema-version-1 Request Document. A canonical `https://huggingface.co/org/repo` reference is equivalent. Bediz converts both forms to that exact HTTPS URL before calling the generic POST installer, avoiding InvokeAI's `org/repo` server-path collision. Variant, subfolder, file, query, and fragment reference forms are unsupported until tested. It asks the anonymous Hugging Face repository metadata API whether the exact repository is public or gated; no token is sent to that API. A denied or absent anonymous result is treated as potentially protected. Bediz then checks InvokeAI's read-only repository metadata for installable files. Multiple checkpoint artifacts return `selection_required` with exact artifact URL candidates; no job is submitted. A Diffusers repository is treated as one package. A repository without a supported artifact fails before mutation. If public access cannot be checked, Bediz fails before mutation rather than assuming the repository is public.

Hugging Face authentication uses InvokeAI's token support through `bediz auth huggingface`. Bediz does not maintain its own token store. On the tested InvokeAI 6.14.1 baseline, a protected repository requires a valid InvokeAI Hugging Face login for metadata access and a separate `--token-stdin` source token for its file downloads; Bediz never reads back the stored login token. If either prerequisite is unavailable, a direct Hugging Face request returns `authentication_failed` and a starter request returns `unsupported_capability` before installation. A starter source or dependency that needs installation and has an unsupported reference form fails before any job is submitted.

`auth huggingface status` reads InvokeAI's `GET /api/v2/models/hf_login` and returns `data.status` as exactly `valid`, `invalid`, or `unknown`. The status reports InvokeAI's verification result; `unknown` is a successful status inspection but does not establish whether a usable token exists. The command never returns the token. Compatible read-only status may run on an untested InvokeAI version when the endpoint is present. `doctor` registers status against the GET endpoint and registers login and logout only for the tested version range with the POST and DELETE methods respectively.

`auth huggingface login --token-stdin` reads a non-empty token from standard input, sends it once as the JSON `token` field to InvokeAI's `POST /api/v2/models/hf_login`, and reports `data.status: "valid"` only when InvokeAI verifies it. An `invalid` response is `authentication_failed` (exit 5); an `unknown` response, malformed successful response, or inconclusive transport result is `outcome_unknown` (exit 6), requiring a new status inspection before another mutation. `auth huggingface logout` sends one `DELETE` to the same endpoint and reports `data.status: "invalid"` when InvokeAI confirms removal. A `valid` response is `invokeai_operation_failed` (exit 6); `unknown`, malformed success, or inconclusive transport returns `outcome_unknown` (exit 6). Conclusive HTTP rejection follows the standard structured error and exit mapping. Neither mutation retries or follows redirects. Both commands return exactly one V1 Result Envelope with `--json`, and human output otherwise; status, success, failure, diagnostics, and receipts never contain the Hugging Face token. Login rejects a configured non-loopback plain-HTTP target before sending the credential.

Protected generic URLs and Civitai downloads accept a token through `--token-stdin`. For URL installation, the flag works with source flags or a Request Document read from a file; an empty standard-input token fails before mutation. Bediz does not persist it; the token never appears in a Request Document, local configuration, receipt, result, or diagnostic. Before a protected URL mutation, Bediz verifies that the tested generic endpoint advertises the `access_token` query parameter. InvokeAI 6.14.1 receives the token in that parameter and stores it in a plaintext temporary install marker while a remote download runs. Bediz omits the complete token-bearing request URL and backend response text from failures, and refuses redirects for that request. Normal terminal handling removes the marker; a paused or interrupted install can retain it for resumption. InvokeAI or proxy access logs are outside Bediz's secrecy guarantee. Bediz rejects token-bearing installation and Hugging Face login over non-loopback plain HTTP. `--request -` and `--token-stdin` cannot be used together because both consume standard input.

User-supplied direct artifact URLs must be HTTP(S) without userinfo, query, or fragment. They fail validation before installation if any of those are present. Civitai page URLs may carry only the explicit `modelVersionId` selector. After validating the selected file belongs to the exact version, Bediz constructs the artifact URL as `https://civitai.com/api/download/models/{version_id}?fileId={file_id}` using verified positive decimal IDs. No other host, path, query key, userinfo, or fragment is allowed for this internally resolved URL; unsupported metadata URL forms fail before mutation. Bediz never echoes a source URL or forwards an artifact URL containing embedded credentials. Installation uses InvokeAI's tested generic POST job endpoint; the Hugging Face-specific GET installation route is not used because it mutates state without returning an inspectable job. Install and authentication mutations require a tested InvokeAI version; compatible read-only status may operate on other versions.

`models install --source-type path --source PATH` and the matching Request Document `{"schema_version":1,"source":{"type":"path","reference":"PATH"}}` require an exact absolute path in the InvokeAI server's filesystem namespace. Bediz does not resolve or inspect that path on the CLI machine. The optional top-level boolean `move` applies only to path sources; omitted or false means in-place registration. Bediz sends `inplace=true` explicitly because InvokeAI 6.14.1 defaults that parameter to false. A true `move` requires execution approval `--yes`, including when the request comes from a document; `--yes` alone does not request a move and is not a document field. An approved move sends `inplace=false` and places the source file in InvokeAI-managed storage. A missing tested `inplace` endpoint parameter fails before mutation. Source tokens do not apply to paths. On the tested 6.14.1 installation, completed in-place registration left the source file at its original absolute path, while completed move removed that source file and placed it in the managed model directory. Both modes return one inspectable install job; an inconclusive submission is `outcome_unknown` and is never replayed automatically.

Model deletion always requires `--yes`. Deleting a managed model removes its files; deleting an in-place registration unregisters it without deleting the source. V1 has no bulk model deletion.

### 14.1 Civitai resolution

Civitai support is deterministic source normalization, not model discovery.

- A direct download URL follows the generic URL validation rules above.
- A positive decimal version identifier or model page URL with an explicit positive `modelVersionId` is resolved through Civitai's model-version metadata.
- A version with one file selects it. When several files exist, exactly one metadata-marked primary file may be selected. Otherwise `selection_required` returns numeric file IDs and names; the caller can resubmit an exact `file_id` belonging to that version.
- A model page without an explicit version never defaults to the newest version; it returns numeric version IDs and names as choices, even if there is only one version.

Bediz provides no Civitai search, ranking, recommendation, or content-policy layer in V1. The creative agent may use its browser to discover a model and then pass the selected reference to Bediz.

## 15. Images, queues, and boards

Image operations use stable InvokeAI image names rather than gallery positions. Upload accepts local files; download writes an explicitly selected image; deletion requires `--yes`.

Queue operations expose InvokeAI batch and item identifiers. Waiting has no total timeout by default; callers may supply `--timeout`. `queue cancel` is explicit and does not require a second confirmation. `queue clear` requires `--yes`.

An output board is optional. With no board identifier, InvokeAI displays the image as Uncategorized. Bediz never inherits the board currently selected in a browser. `boards list`, `boards get`, and `boards create` are supported. Board deletion is deferred until its effect on contained images has a separate destructive-operation contract.

### 15.1 Inspection and upload operations

The first management slice provides `models list`, `images list`, `images get`, `images upload`, `queue list`, and `queue get`. Other model, image, and queue commands remain separate delivery slices.

Each operation accepts a typed request document with `schema_version: 1`. Convenience flags and positional arguments compile to the same request values. Operation inputs cannot be combined with `--request`.

`models list` accepts optional exact `base_models`, `model_type`, `model_format`, and `model_name` filters. Its result is sorted by model name and then model key. A model summary contains only the stable model key, name, base, type, format, optional size in bytes, and optional description. Bediz does not expose model filesystem paths, hashes, source API responses, or source URLs in this result.

`images list` accepts `offset`, `limit`, optional `board_id`, and `include_intermediate`. The defaults are offset zero, limit twenty, and no intermediate images. Limits below one or above one hundred are invalid local requests and return exit status 2. Results are newest first. `images get` requires one exact InvokeAI image name. Image results contain an Image Reference with the stable image name, dimensions, origin, category, timestamps, intermediate and starred status, optional board, session and node identifiers, workflow availability, and absolute full-image and thumbnail URLs.

`images upload` requires an absolute local file path. Bediz validates that the path names a readable regular file before making a request. It uploads the file as a non-intermediate user image without resizing, injected metadata, or an implicit board. A successful result contains the uploaded Image Reference. Upload is available only when the InvokeAI version is in the supported range.

`queue list` accepts a queue identifier, offset, and limit. The queue identifier defaults to `default`, offset defaults to zero, and limit defaults to twenty. Limits below one or above one hundred are invalid local requests and return exit status 2. Results are newest first and contain lightweight queue-item summaries rather than execution graphs. `queue get` requires an item identifier and returns normalized identifiers, status, priority, origin, destination, timestamps, a concise error when present, and Image References for completed image outputs when available. Bediz does not expose raw execution graphs or server tracebacks.

Read-only inspection results are normalized Bediz values rather than passthrough InvokeAI response documents. This keeps the V1 JSON shape stable and prevents backend-only or sensitive fields from becoming part of the public contract.

### 15.2 Inspection safety

List results contain no more than the requested page. For queue listing against the supported InvokeAI 6.14.x API, Bediz first retrieves the complete lightweight, ordered item-ID index because that endpoint does not support pagination. This index response may grow with the queue and is constrained by the configured HTTP response-size limit. Bediz then selects the requested offset and limit from the index, hydrates only those IDs through the lightweight summary endpoint, preserves the index ordering and reported total count, and never fetches queue-item execution graphs. Summary hydration and public output are therefore page-bounded even though retrieval of the backend ID index is not.

Read-only requests may use a GET or a semantically read-only POST endpoint. Retry safety is determined by operation semantics, not only by the HTTP method. Transient read failures may be retried within the configured limit.

Image upload is sent once and is never retried automatically. A connection failure after InvokeAI may have accepted the upload returns `outcome_unknown` with exit status 6. Authentication and connection failures return exit status 5; invalid local requests return exit status 2; conclusive InvokeAI operation failures return exit status 6.

## 16. Profiles

Profiles are schema-versioned JSON documents in the per-user operating-system configuration directory. V1 has no project-local or cloud profile lookup.

A profile may contain:

- Model and component preferences
- Width and height
- Applicable generation settings
- Applicable upscale settings

A profile does not contain prompts, seeds, source images, output boards, tokens, or other secrets.

Creating an existing name fails unless both `--replace` and `--yes` are supplied. Replacement is atomic. Bediz retains no profile revision history; schema versioning does not mean historical revisions.

## 17. Retry, timeout, and uncertain outcomes

Bediz may retry safe read-only requests a limited number of times after transient failures. It never automatically retries enqueue, install, delete, cancel, or other mutations.

If a connection fails after InvokeAI may have accepted a mutation, Bediz returns `outcome_unknown`. The caller inspects the relevant queue, model, board, or image state before deciding whether to submit another request.

Ordinary connection and HTTP calls have bounded timeouts. Generation and queue waiting have no total timeout unless `--timeout` is supplied. An elapsed wait deadline returns `wait_timeout` and never cancels the remote item.

## 18. Approval and destructive operations

Generation, upscale, image upload, enqueue, waiting, and queue cancellation require no additional CLI approval.

Delete, bulk-clear, profile replacement, and moving model files require explicit `--yes` as specified by their commands.

The agent skill may install a model without another confirmation when the user explicitly requested that model be installed or used. When a normal creative request merely reveals a missing model, the skill first reports the source, approximate size, and known license information and obtains installation consent. It prefers compatible installed models when possible.

## 19. Agent skill

The repository ships one canonical `skills/bediz/SKILL.md`. It teaches a creative agent to:

- Run readiness checks when capability state is unknown.
- Inspect installed models and resolve exact identifiers.
- Translate user intent into typed Bediz requests.
- Use `--json` and structured errors.
- Improve unspecified prompts and settings without overriding explicit constraints.
- Handle `selection_required`, `outcome_unknown`, and synchronization warnings safely.
- Use browser research for discovery while leaving deterministic installation and execution to Bediz.
- Obtain installation consent when required.

The skill contains no graph-building logic or private InvokeAI payload construction. Other agent systems may use thin adapters derived from the canonical skill.

## 20. Security and licensing

Bediz redacts installation request URLs and projects only safe backend job fields; InvokeAI's own temporary install markers and any upstream access logs are governed by the source-token boundary in section 14. ## 21. Release targets

Initial release artifacts are:

- Linux amd64
- Windows amd64
- macOS arm64
- SHA256 checksum files
- `go install` support

Package-manager formulas, a self-updater, additional architectures, and signed installers are deferred.

## 22. Verification strategy

The graph compiler and request resolution are pure and covered by unit tests. Each advertised family has versioned graph fixtures and validation tests. API behavior is tested against the InvokeAI 6.14.1 OpenAPI contract, and meaningful end-to-end tests run against a live local InvokeAI instance.

Compatibility tests verify that unsupported fields and versions fail explicitly, component ambiguity returns candidates, JSON standard output remains parseable, unsafe mutations are not retried, and Recall failures become warnings without changing successful generation outcomes.

## 23. Delivery sequence

1. Go foundation, configuration, HTTP client, JSON envelope, and `doctor`.
2. Safe model, image, and queue inspection plus image upload.
3. End-to-end Anima generation, polling, and execution receipt.
4. Generation Recall and UI synchronization.
5. Model installation, authentication, and source resolvers.
6. SDXL and FLUX.1 generation adapters.
7. SD1.5 and SDXL generative upscale.
8. Boards, profiles, and remaining safe management commands.
9. Canonical agent skill, cross-platform release builds, and checksums.

## 24. V1 acceptance

V1 is accepted when all advertised commands and family combinations pass their tests on the supported InvokeAI range, unsupported combinations fail explicitly, the capability matrix and `doctor` agree, the JSON contract is stable, the canonical skill can complete an end-to-end generation through Bediz, and the documented release artifacts are reproducible.

# Bediz V1 Specification

## 1. Purpose

Bediz is an open-source deterministic CLI through which a creative AI agent and a human use the same local InvokeAI installation. The agent interprets creative intent and chooses prompts and settings. Bediz validates those explicit choices, compiles supported operations into InvokeAI execution graphs, submits them through InvokeAI's API, and returns stable machine-readable results. The human can observe queue activity and outputs in InvokeAI's web interface and continue the work there.

Bediz does not call an LLM, make creative decisions, reproduce browser gestures, or fork InvokeAI.

## 2. V1 outcomes

V1 provides:

- Basic text-to-image and image-to-image generation for Anima, SDXL, and FLUX.1.
- Tiled generative upscale for SD1.5 and SDXL.
- Prompt, model, image-size, generation-setting, output-count, seed, and board control where applicable.
- Ordered LoRAs for SDXL, Anima, and FLUX.1 text-to-image and image-to-image generation.
- Queue submission, inspection, waiting, cancellation, and explicit clearing.
- Gallery image inspection, upload, download, and explicit deletion.
- Model inspection, installation, status, local scanning, and explicit deletion.
- Model sources from InvokeAI starter models, Hugging Face, direct URLs, local paths, and strict Civitai URL resolution.
- Board inspection and creation.
- Local technical generation profiles.
- Version, schema, component, and capability diagnostics.
- Parameter Recall and operation-specific UI synchronization levels.
- A canonical agent skill.

V1 does not provide Canvas brush or layer control, arbitrary workflow authoring, inpainting, reference images, ControlNet generation, external hosted generation models, video generation, a daemon, a local audit database, a public graph dry-run command, or a general browser-automation layer.

## 3. Product boundary

### 3.1 Creative agent

The creative agent understands the user's intent, improves prompts, selects installed models, chooses technical settings, and decides which explicit Bediz operations to request. It preserves every model, prompt, and setting the user fixes explicitly.

### 3.2 Bediz controller

Bediz performs deterministic validation, model and component resolution, graph compilation, InvokeAI API calls, polling, result normalization, and UI Recall. It never invents creative content or silently changes an unsupported setting.

### 3.3 InvokeAI

InvokeAI remains the execution engine and the source of truth for models, queues, boards, images, metadata, and results. Bediz stores no duplicate job database or audit history.

## 4. Architecture

Bediz is a standalone Go application distributed as a single binary. Its internal typed operation layer is independent from the CLI parser. CLI flags and JSON request documents compile to the same operation types.

The controller uses HTTP APIs and polling in V1. Socket.IO support may be added later. Graph-producing operations use versioned family adapters and a pure, testable graph compiler. The live OpenAPI document validates endpoint and invocation vocabulary, but family-specific graph topology remains Bediz's responsibility.

Browser automation is not part of the normal control path. Bediz runs no daemon and requires no Python environment.

## 5. InvokeAI compatibility

The initial supported range is:

```text
>= 6.14.1, < 6.15.0
```

InvokeAI 6.14.1 is the baseline integration-test version. Later 6.14 patch releases must pass live compatibility checks. A new minor or major version is unsupported until the capability matrix is updated.

Read-only inspection and `doctor` may operate on an untested version when their endpoints are compatible. Graph-producing operations fail with `unsupported_capability`. V1 has no `--allow-untested` override.

Every command that requires the supported range reads the InvokeAI version before any other InvokeAI request and classifies the answer the same way `doctor` does. A readable version outside the range returns `unsupported_capability` with exit status 4. An answer without a version returns `invalid_version_response`, and an unreadable version returns `invalid_invokeai_version` with the reported `version` in its details. Both have exit status 6.

The capability matrix records implemented and tested support by InvokeAI version, operation, model family, setting, and UI synchronization level. An operation is registered and reported as compatible only when its implementation and compatibility fixtures exist.

Commands default to concise human-readable output. `--json` selects the stable machine contract. Colors are disabled when output is non-interactive.

## 7. Connection and configuration

Connection values resolve in this order:

1. `--url` and `--token`
2. `BEDIZ_URL` and `BEDIZ_TOKEN`
3. Per-user Bediz configuration
4. `http://127.0.0.1:9090`

V1 has one active target and no named target profiles. The primary deployment is Bediz and InvokeAI on the same machine. Single-user InvokeAI requires no token. Tokens are never logged.

For InvokeAI authentication, prefer `BEDIZ_TOKEN` from an existing credential source or a stored token. `--token` remains supported with the precedence above, but its value is visible in process arguments and can enter shell history when supplied literally. Remote-command help and the Agent Skill recommend the environment or stored configuration.

`config set --token-stdin` reads the InvokeAI bearer token from standard input, trims surrounding whitespace, and requires a non-empty value. It persists the token through the same atomic, user-only configuration write as `config set --token`, without requiring the credential in process arguments. It may accompany `--url` or `--unset-url`, but cannot be combined with `--token` (including an explicitly empty value) or `--unset-token`. Flag conflicts are rejected before reading standard input. An empty token, an input read failure, or conflicting flags returns `invalid_request` with exit status 2 and leaves the stored configuration unchanged. Configuration command output never contains the token; `config set` argument errors omit parser text that could echo an accidentally supplied credential. Connection resolution and the configuration file schema do not change.

## 8. Request contract

### 8.1 Canonical representation

Each operation has a typed JSON request document with required `schema_version: 1`. A request may be read from a file or standard input:

```text
bediz generate --request request.json
bediz generate --request -
```

Common operation flags are a convenience representation of the same request. Operation-field flags cannot be combined with `--request`. Connection, output, wait, and timeout flags may accompany it because they do not alter operation semantics.

Unknown request fields are validation errors. Bediz does not ignore misspelled or inapplicable settings. Member names match the documented names exactly, including case, at every nesting depth; a name that differs only in case is an unknown field. A repeated member name is a validation error. An explicit `null` member value or list element is a validation error: an optional field is omitted, never null. A request document must contain exactly one JSON value, and that value must be an object.

### 8.2 Exact selectors

Installed models are selected by InvokeAI model key. Model and board names are accepted only when they resolve uniquely. Ambiguity returns `selection_required` with structured candidates; no interactive terminal picker is used.

### 8.3 Defaults

Generation values resolve in this order:

1. Model-family defaults
2. Named generation profile
3. Explicit request values

The creative agent selects the main model unless a profile or user constraint already identifies it. Bediz may resolve required auxiliary components under the component-resolution rules.

`generate` loads a named profile during local validation, before any InvokeAI request. The explicit main-model selector wins over the profile's selector; one of them must be present. For each applicable technical setting, an explicit request value wins over the profile value, which wins over the selected family's default. Width and height form one value for precedence: an explicit pair replaces the profile pair, and otherwise the profile pair replaces the family pair.

## 9. Result and error contract

With `--json`, standard output contains exactly one final JSON object:

```json
{
  "schema_version": 1,
  "ok": true,
  "operation": "generate",
  "data": {},
  "warnings": []
}
```

Errors use the same envelope with a structured `error` containing a stable code, message, and relevant details. Progress and diagnostics never contaminate JSON standard output; necessary operational messages use standard error.

`invalid_request` includes optional `error.details.field` when the decoder or operation validator provides a field location. It names a Request Document member path, using dots for nested members and zero-based indexes for list elements (for example, `components.vae` or `base_models.1`). Unknown members retain their input spelling, such as `widht`. Document decoding supplies this location for unknown, repeated, explicit `null`, and incorrectly typed members or list elements. Generation dimension-pair errors name the missing dimension (`height` when only `width` is supplied, and conversely); an unsupported generation scheduler names `scheduler`. Convenience flags report the same Request Document keys. Errors without an identified field omit `field`; callers then inspect the other details and message.

Every invalid generation Denoising Strength names `strength` in `error.details.field`, including a strength without a Source Image.

Invalid LoRA lists name `loras`; invalid selectors and weights name `loras.<zero-based index>.model` and `loras.<zero-based index>.weight`, respectively, for flags and documents alike. Unknown or null LoRA members use the same paths, with the unknown member's input spelling.

`invokeai_operation_failed` may include optional `error.details.invokeai_detail` for a conclusive, non-private HTTP 4xx rejection. This is best-effort diagnostic information: its field name, sanitization, and bounds are part of V1, while its presence and backend text depend on InvokeAI. Callers branch on the stable error code and HTTP status rather than interpreting this text. Bediz reads the FastAPI `detail` before truncating the backend body. A string detail becomes a normalized string; a validation-error array retains only `msg`, optional `type`, and an optional `loc` of string member names and non-negative integer indexes. Inputs, exception context, other backend fields, and raw response bodies are not forwarded through this field. Malformed JSON, invalid UTF-8, duplicate members, empty details, and unsupported detail shapes omit it; an invalid location is omitted rather than guessed.

The diagnostic value contains at most 4096 bytes of encoded JSON, at most eight validation errors, and at most sixteen location segments per error. Messages and string details are capped at 512 UTF-8 bytes; types and string location segments are capped at 128 UTF-8 bytes. Text truncation preserves UTF-8 and ends with an ellipsis. Control and Unicode format characters and repeated whitespace are normalized, and the configured InvokeAI bearer token is redacted before truncation. Array entries stop at the size or count limit; a detail with no retained entries is omitted. Private installation and Hugging Face authentication requests omit the entire diagnostic value, as they omit backend response bodies. Authentication, not-found, server-error, redirect, and unknown-outcome classifications retain their existing behavior.

V1 does not provide JSON Lines progress events. A caller may use `--no-wait` and later call `queue get` or `queue wait`.

Process exit statuses are:

- `0`: success
- `2`: invalid request
- `3`: selection required
- `4`: incompatible or unsupported capability
- `5`: connection or authentication failure
- `6`: InvokeAI operation failure
- `130`: interrupted locally

## 10. Diagnostics

`bediz doctor` is a readiness check, not a connectivity ping. It reports:

- Bediz and InvokeAI versions.
- Connection and authentication status.
- OpenAPI availability and the endpoints required by registered capabilities.
- Invocation types and fields required by registered capabilities.
- Installed main and component models relevant to registered capabilities.
- Capability-matrix matches and failures.
- UI synchronization levels for registered operations that support synchronization.

When OpenAPI cannot be retrieved or decoded, `openapi.available` is `false` and `openapi.required_endpoints` and `openapi.required_invocations` are omitted because their compatibility is unknown. The report retains the request or decoding issue and the `openapi_unavailable` capability failures. It does not infer missing endpoints, invocations, or properties from an unread document. When OpenAPI loads successfully, both lists retain the full compatibility checks and any missing-property details, including for an incompatible document.

An operation without a tested implementation is absent from the report. The capability matrix advertises `generate/anima`, `generate/sdxl`, and `generate/flux` entries for both `mode: "txt2img"` and `mode: "img2img"`, only when their tested endpoint and invocation schemas and required installed models are present. SDXL requires an installed `sdxl` main model; its optional VAE override is not an installed-model requirement. Anima requires an installed Anima main model, Anima VAE, and Qwen3 encoder for both modes. FLUX.1 requires a `flux` main model with variant `dev` or `schnell` and format `checkpoint`, `bnb_quantized_nf4b`, or `gguf_quantized`, plus a FLUX VAE and T5 and CLIP Embed models with base `any`. UI Synchronization is advertised only when Recall is compatible, including the `cfg_scale` patch field used by SDXL. All image-to-image entries add image inspection and upload endpoints and `img_resize` input properties `image`, `width`, `height`, `resample_mode`. SDXL additionally requires `i2l` properties `image`, `vae`, `fp32`, `color_compensation`, and `denoise_latents.latents`. Anima additionally requires `anima_i2l` properties `image` and `vae`, and `anima_denoise.latents`. FLUX.1 additionally requires `flux_vae_encode` properties `image` and `vae`, and `flux_denoise` properties `latents`, `denoising_start`, `denoising_end`, and `add_noise`. All require `core_metadata` properties `strength` and `init_image`. Each schema keeps the common `id`, `is_intermediate`, `use_cache`, and `type` properties. A missing property makes only the image-to-image entry incompatible when text-to-image does not require it. The same vocabulary is checked before source upload or enqueue. The FLUX.1 text-to-image entry's requirements are unchanged.

The additional `generate/sdxl` row with `setting: "loras"` has no `mode` or `ui_sync` member. It inherits the SDXL text-to-image requirements and adds `SDXLLoRALoaderInvocation` (`sdxl_lora_loader`) properties `lora`, `weight`, `unet`, `clip`, and `clip2`, plus `CoreMetadataInvocation.loras`. Both schemas also require the common `id`, `is_intermediate`, `use_cache`, and `type` properties. This row requires no installed LoRA; `ready` does not depend on a LoRA model or the new LoRA-only schema and properties. A missing LoRA loader schema or property affects only this row. A missing `core_metadata.loras` affects the LoRA row and leaves the Generation Mode rows compatible. A missing inherited requirement also affects the modes that require it. Human output names this row `generate/sdxl/loras`. A LoRA request checks its mode requirements and the LoRA additions before any source upload or enqueue; a request without LoRAs checks only its existing mode row.

The additional `generate/anima` row with `setting: "loras"` likewise has no `mode` or `ui_sync` member. It inherits the Anima text-to-image requirements and adds `AnimaLoRALoaderInvocation` (`anima_lora_loader`) properties `lora`, `weight`, `transformer`, and `qwen3_encoder`, plus `CoreMetadataInvocation.loras`. Both schemas require the common `id`, `is_intermediate`, `use_cache`, and `type` properties. The row requires no installed LoRA, so `ready` does not depend on one. A missing `anima_lora_loader` schema or property affects only this row; a missing `core_metadata.loras` affects every LoRA row while leaving every Generation Mode row compatible. Human output names the row `generate/anima/loras`. An Anima LoRA request checks its mode and LoRA requirements before source upload or enqueue; a LoRA-less request checks only its mode requirements.

The additional `generate/flux` row with `setting: "loras"` has no `mode` or `ui_sync` member. It inherits the FLUX.1 text-to-image requirements and adds `FluxLoRALoaderInvocation` (`flux_lora_loader`) properties `lora`, `weight`, `transformer`, `clip`, and `t5_encoder`, plus `CoreMetadataInvocation.loras`. Both schemas require the common `id`, `is_intermediate`, `use_cache`, and `type` properties. It requires no installed LoRA. A missing `flux_lora_loader` schema or property affects only this row; a missing `core_metadata.loras` affects all three LoRA rows while leaving every Generation Mode row compatible. Missing inherited requirements affect the modes requiring them too. Human output names the row `generate/flux/loras`. A FLUX.1 LoRA request checks its mode and LoRA requirements before source upload or enqueue; a LoRA-less request checks only its mode requirements.

Text-to-image `generate` and `upscale` also check their capability entry's endpoints before source upload or enqueue. A missing endpoint returns `unsupported_capability` with the required method and path, as image-to-image does. For each operation, a compatible `doctor` row implies its InvokeAI compatibility preflight passes. UI Synchronization uses the Recall common requirements and the generation family's additional Recall fields (`cfg_scale` for SDXL); upscale uses the common fields. The `recall` row contains the common requirements plus every generation family's additional fields, so it can be stricter than standalone `recall`.

`upscale/sdxl` and `upscale/sd-1` each require the tested version, enqueue, image inspection, and image upload (`POST /api/v1/images/upload`) endpoints, the family's upscale invocation vocabulary (including metadata fields allowed by `core_metadata`), and installed models: a `normal` main model of that base, a Spandrel image-to-image model, and a ControlNet of that base. SDXL's vocabulary includes `sdxl_model_loader` and `sdxl_compel_prompt`; SD1.5's includes `main_model_loader`, `clip_skip`, and `compel`. The SD1.5 main model may have any format InvokeAI's SD1.5 loader accepts. These model checks establish presence only; InvokeAI records neither a ControlNet's Tile purpose nor a Spandrel model's scale. The upload endpoint is required because the upscale contract includes local-file sources; without it both entries are incompatible and name the missing endpoint. Both entries carry `ui_sync: partial` only when Recall is also compatible.

Recall readiness is reported separately from Direct Execution readiness for every registered generation family and upscale family. A missing Recall endpoint or an incompatible Recall patch schema fails the `recall` capability with the missing requirement named; it does not make a compatible `generate` or `upscale` capability incompatible. `ui_sync.generate` and `ui_sync.upscale` are each `partial` only when the supported version, Direct Execution for at least one registered entry of that operation, and tested Recall requirements are all compatible. Each is omitted when those requirements are not met.

The `recall` row checks the common patch fields and `cfg_scale`, which SDXL automatic UI Synchronization sends. It continues to report `incompatible_recall_schema:cfg_scale` when that field is absent. Standalone `recall` checks only the common fields and can succeed on that installation; the row also gates UI Synchronization and therefore remains stricter.

V1 synchronization status on stock InvokeAI 6.14.x is:

```json
{
  "ui_sync": {
    "generate": "partial",
    "upscale": "partial"
  }
}
```

## 11. Generation

### 11.1 Supported families

- Anima
- SDXL
- FLUX.1

Anima, SDXL, and FLUX.1 have tested graph adapters.

### 11.2 Core fields

A generation request supports, where applicable:

- Exact main-model key
- Positive prompt and optional negative prompt
- Width and height
- Steps
- Scheduler
- Guidance or CFG scale
- Seed
- Output count
- Output board identifier
- Supported explicit component overrides

Width and height are supplied together or both resolve from a profile or family default. When `source` is present, omitted dimensions resolve from the Source Image as §11.7 defines, not from a profile or family default. Bediz validates family bounds and alignment. Aspect-ratio presets are not part of the canonical V1 request.

Steps, scheduler, guidance, CFG, and negative prompts are typed, family-aware settings. Supplying a field whose semantics are unsupported for the selected family is an error.

Schema version, positive prompt, paired explicit dimensions, unknown fields, and any named profile are checked before any network request. A generation request may omit `model` when its profile supplies one; a request with neither returns `invalid_request` before network access. A missing profile returns `not_found`, and a profile without a `generate` section returns `invalid_request`, both before network access. The main-model selector then resolves across all installed main models by exact Model Key or unique name. Its base selects a registered Model Family adapter; a model of an unregistered base returns `unsupported_capability`. Family-specific settings, including dimension alignment, scheduler, guidance, negative-prompt and component applicability, are validated after main-model resolution and before enqueue. Inapplicable settings return `invalid_request` (exit status 2). An inapplicable profile setting returns details `{"source":"profile","profile":NAME,"field":FIELD}` even when an explicit request value would override it. A shared name returns `selection_required` with candidates sorted by Model Key.

V1 exposes no arbitrary `--advanced key=value` escape hatch.

The schema-version-1 Generation Request uses these canonical JSON field names:

- `schema_version`
- `model`
- `profile`
- `positive_prompt`
- `negative_prompt`
- `width` and `height`
- `steps`
- `scheduler`
- `guidance`
- `seed`
- `output_count`
- `board_id`
- `components`, containing typed `vae`, `qwen3_encoder`, `t5_encoder`, and `clip_embed` selectors. SDXL accepts only an optional `vae` override. Anima accepts `vae` and `qwen3_encoder`. FLUX.1 accepts `vae`, `t5_encoder`, and `clip_embed`. Inapplicable selectors are rejected.
- `loras`, the optional ordered list in §11.8.

The matching convenience flags are `--model`, `--profile`, `--prompt`, `--negative-prompt`,
`--width`, `--height`, `--steps`, `--scheduler`, `--guidance`, `--seed`,
`--output-count`, `--board`, `--vae`, `--qwen3-encoder`, `--t5-encoder`, `--clip-embed`, and repeatable `--lora`.

The optional `source` and `strength` fields and `--image`, `--image-path`, and `--strength` flags select the image-to-image behavior in §11.7. Omitting `source` retains text-to-image behavior exactly.

For Anima, omission resolves without consulting browser state: the negative
prompt becomes empty, dimensions become 1024 by 1024, steps become 30, the
scheduler becomes `euler`, guidance becomes 4.5, and output count becomes one.
Explicit request values override these family defaults. Width and height must
be supplied together and resolve to positive multiples of 8; steps and output
count must be positive; guidance must be finite and at least 1; and a seed must
be an unsigned 32-bit integer. The supported Anima schedulers are `euler`,
`heun`, `dpmpp_2m`, `dpmpp_2m_sde`, `er_sde`, and `lcm`. The Anima capability
accepts any positive output count. InvokeAI queue-capacity rejection remains a
conclusive operation failure rather than a Bediz-specific arbitrary maximum.

For SDXL, omission resolves to an empty negative prompt, 1024 by 1024 dimensions,
30 steps, scheduler `dpmpp_3m_k`, guidance 7.0, and one output. Width and height
must be positive multiples of 8; steps and output count must be positive;
guidance is a finite SDXL CFG scale of at least 1. The supported InvokeAI 6.14.1
schedulers are `ddim`, `ddpm`, `deis`, `deis_k`, `lms`, `lms_k`, `pndm`, `heun`,
`heun_k`, `euler`, `euler_k`, `euler_a`, `kdpm_2`, `kdpm_2_k`, `kdpm_2_a`,
`kdpm_2_a_k`, `dpmpp_2s`, `dpmpp_2s_k`, `dpmpp_2m`, `dpmpp_2m_k`,
`dpmpp_2m_sde`, `dpmpp_2m_sde_k`, `dpmpp_3m`, `dpmpp_3m_k`, `dpmpp_sde`,
`dpmpp_sde_k`, `er_sde`, `unipc`, `unipc_k`, `lcm`, and `tcd`. SDXL accepts a
negative prompt. SDXL style prompts equal the corresponding positive and
negative prompts. Supplying `qwen3_encoder`, `t5_encoder`, or `clip_embed`
selectors is `invalid_request`.

For FLUX.1, an installed `flux` main model must have Model Variant `dev` or `schnell` and a stock 6.14.1 loader-accepted format: `checkpoint`, `bnb_quantized_nf4b`, or `gguf_quantized`. Krea dev and Kontext dev report variant `dev` and are accepted for text-to-image when their format is supported. Variant `dev_fill`, an absent or unknown variant, SDNQ, ordinary `diffusers`, and other formats are `unsupported_capability` before enqueue. The ordinary FLUX Diffusers config is rejected by the stock 6.14.1 FLUX model loader even though InvokeAI can record such a model in inventory. Defaults are 1024 by 1024, scheduler `euler`, and one output. Dev defaults to 30 steps and distilled guidance 4.0; schnell defaults to 4 steps and has no guidance. Dimensions are positive multiples of 16, steps and output count are positive, and schedulers are `euler`, `heun`, and `lcm`. Dev guidance must be finite and at least 1. Supplying guidance for schnell or a non-empty negative prompt for either variant is `invalid_request`. FLUX.1 uses fixed CFG scale 1.0, which is not a public setting. `qwen3_encoder` is inapplicable.

### 11.3 Seeds and multiple outputs

When the request omits a seed, Bediz assigns a valid random seed to each output before submission. When it supplies a seed for multiple outputs, the first output uses that seed and later outputs increment it sequentially within the family's valid range. Every resolved seed appears in the execution receipt.

### 11.4 Component resolution

Bediz queries installed model inventory for family-required auxiliary components:

- An explicit request override wins.
- A profile preference is used when compatible.
- One compatible installed component is selected automatically.
- Multiple compatible candidates return `selection_required`.
- No compatible component returns a structured missing-component error with install guidance when known.

A profile preference resolves by exact key or unique name to one installed model with the required base and type. An explicit request component selector wins without consulting its profile preference. An incompatible, ambiguous, or absent profile preference is skipped, and the ordinary automatic resolution above continues. Each skip produces `{"code":"profile_preference_skipped","message":...,"details":{"profile":NAME,"component":KIND,"reason":"incompatible"|"ambiguous"|"not_found"}}`. The warning appears in the failure Result Envelope if fallback component resolution or another later step fails before an accepted enqueue, including compatibility checks, Source Image validation or upload, compilation, and enqueue rejection or an inconclusive result. When execution succeeds, it appears in both the Result Envelope and Execution Receipt. An upload response with an image name whose image or thumbnail URL cannot be normalized reports the retained Source Image but omits profile preference warnings; failures after an accepted enqueue also omit them. A profile component kind inapplicable to the resolved family returns `invalid_request` with the profile source, name, and field instead of a skip. For SDXL, a compatible profile VAE acts as the VAE override; a skipped preference leaves the bundled VAE in use.

Bediz never chooses the first arbitrary installed model.

Anima, SDXL, and FLUX.1 are registered generation families; other bases remain unsupported until their tested adapters are registered. The tested Anima component combination is a VAE
with base `anima` and type `vae` plus an encoder with base `any` and type
`qwen3_encoder`. An explicit compatible key or unique name wins; without a
selector, exactly one compatible installed component is selected. Ambiguous
names or several automatic candidates return `selection_required` (exit status
3) with candidates sorted by Model Key. An absent automatic component returns
`missing_component` (exit status 4) with its component type, required base and
type, and installation guidance. SDXL accepts an optional VAE override with
base `sdxl` and type `vae`, resolved by exact key or unique name. Without an
override, its main model's bundled VAE is used; Bediz does not automatically
select an installed VAE, and `component_keys` is empty. An override records
`{"vae":"<key>"}` in `component_keys`. An ambiguous override returns
`selection_required`; an incompatible one returns `unsupported_capability`.
An explicitly empty SDXL VAE selector is `invalid_request`.
FLUX.1 requires a VAE with base `flux` and type `vae`, a T5 encoder with base `any` and type `t5_encoder`, and a CLIP Embed model with base `any` and type `clip_embed`. Each uses an explicit compatible override first, then a compatible profile preference, then exactly one compatible installed model. Missing and ambiguous selections use the same structured results as Anima. The OpenAPI-described SDNQ self-contained component fallback remains unsupported until its tested slice.

### 11.5 Submission and completion

`generate` compiles an execution graph and submits it to InvokeAI's default queue. It waits for completion by default. `--no-wait` returns accepted queue identifiers.

For Anima on InvokeAI 6.14.x, the tested graph contains one
`anima_model_loader`, one positive `string` input, positive and negative
`anima_text_encoder` nodes with their `collect` nodes, one `integer` seed,
one `anima_denoise`, one `core_metadata`, and one `anima_l2i` output node.
Typed edges carry the loaded transformer, Qwen3 encoder, VAE, prompt
conditioning, seed, denoised latents, and metadata to their consumers. Model
inputs use complete InvokeAI Model Identifiers. The denoise and metadata nodes
contain the resolved dimensions, steps, scheduler, guidance, negative prompt,
model, VAE, and Qwen3 encoder, while edges carry the positive prompt and seed
into metadata. Node identifiers may vary without changing this contract.

For SDXL on InvokeAI 6.14.x, the tested text-to-image graph contains
`sdxl_model_loader`, positive and negative `sdxl_compel_prompt` nodes with
matching prompt and style inputs, `noise`, `denoise_latents`, `core_metadata`,
and a non-intermediate `l2i` output. The graph includes the stock string,
conditioning collection, and integer seed nodes. An optional override adds
`vae_loader`; otherwise the model loader's bundled VAE feeds `l2i`. The noise
node uses the resolved dimensions and the batch seed; the denoiser uses the
resolved steps, scheduler, and CFG scale. `l2i` uses the stock fp32 setting
(`true`) and carries the optional board. Metadata records the resolved
settings and model identifiers, including an explicit VAE when selected.
Complete InvokeAI Model Identifiers are used throughout.

For FLUX.1 on InvokeAI 6.14.1, the tested text-to-image graph contains `flux_model_loader` with explicit T5, CLIP Embed, and VAE identifiers; one positive `flux_text_encoder` with the loader's variant-specific `max_seq_len`; `flux_denoise` with CFG scale 1.0; `core_metadata`; and a non-intermediate `flux_vae_decode` output with an optional board. The loader supplies transformer, CLIP, T5, and VAE outputs. The batch uses the ordered seed association described below.

One logical generation is submitted in one `enqueue_batch` mutation to the
`default` queue. Bediz never automatically retries that mutation. Before that
mutation, Bediz resolves the complete ordered seed set and compiles one
InvokeAI batch that produces one queue item per seed. For InvokeAI 6.14.x, the
adapter orders the batch seed values so the returned `item_ids` and
`resolved_settings.seeds` describe the same outputs at the same positions.

Waiting polls read-only queue inspection for each accepted item, preserving the
enqueue response order, until every item reaches a terminal state. Polling
never replays the enqueue mutation and never calls a cancellation endpoint.
InvokeAI 6.14 queue items use `pending`, `in_progress`,
`waiting`, `completed`, `failed`, and `canceled`; the first three are
non-terminal, where `waiting` means the item is suspended while a workflow-call
child item runs. A status outside this tested set fails with
`invalid_invokeai_response` instead of being treated as terminal or polled
indefinitely. Waiting has no total timeout; when supplied, `--timeout` bounds
only the local wait while every HTTP request keeps its own bounded transport
timeout. An elapsed wait deadline returns `wait_timeout` with `queue_id`,
`batch_id`, the accepted `item_ids`, and `pending_item_ids`; local interruption
returns `interrupted` with the same details. `pending_item_ids` lists the
accepted items not yet observed as terminal when waiting stopped, in queue item
order: the item being waited on and every later accepted item. A later item may
already be terminal in InvokeAI without having been observed by Bediz.

Interrupting a waiting Bediz process or reaching a local wait deadline does not
cancel the InvokeAI item. Cancellation is a separate `queue cancel` operation.

### 11.6 Execution receipt

A completed request returns:

- The submitted request
- Fully resolved settings
- Exact main and component model keys
- Queue batch and item identifiers
- Per-output seeds
- Image references and InvokeAI URLs
- Output board
- UI synchronization warnings

Generated images remain in InvokeAI. Local download is an explicit `images download` operation.

The schema-version-1 Execution Receipt uses these fields:

- `submitted_request`: the canonical Generation Request before defaults or automatic component resolution, retaining `profile` when supplied.
- `resolved_settings`: the resolved prompts, dimensions, steps, scheduler,
  guidance, output count, optional board identifier, applied `profile`, exact `model_key`, typed
  `component_keys`, and ordered `seeds`.
- `resolved_settings.guidance` is omitted for FLUX.1 schnell. FLUX.1 `component_keys` contains `vae`, `t5_encoder`, and `clip_embed`.
- `queue`: the `queue_id`, `batch_id`, and ordered `item_ids` returned by InvokeAI.
- `outputs`: ordered item, seed, and Image Reference associations; this is an
  empty array in an accepted `--no-wait` receipt.
- `warnings`: profile preference and UI synchronization warnings, also present in the Result Envelope.

For image-to-image, `submitted_request` retains `source` and any submitted `strength`; the receipt adds `source_image` and `source_uploaded`, and `resolved_settings` adds the resolved `strength`. These members are omitted in text-to-image receipts.

With LoRAs, `submitted_request.loras` retains the ordered input and any omitted weights, while `resolved_settings.loras` contains ordered `{ "model_key": ..., "weight": ... }` records with resolved weights. Both members are omitted from LoRA-less receipts.

A completed item yields exactly one output record per queue item: the item
identifier, the resolved seed at the same position in `resolved_settings.seeds`,
and the normalized Image Reference with its absolute InvokeAI image and
thumbnail URLs. Bediz verifies that same-position association against each
queue item's recorded batch seed. Missing or contradictory seed metadata, or a
completed item that exposes no image output or more than one, fails with
`invalid_invokeai_response` instead of a guessed association. If any item in a
batch fails or is canceled, the generation fails with
`invokeai_operation_failed`, the accepted queue identifiers, and a concise
normalized message; a partially completed batch is never reported as a
successful receipt, and server tracebacks are never exposed.

### 11.7 Image-to-image

The Generation Mode is inferred from `source`. `source` has the same strict Source Image shape as upscale: `{ "type": "image", "reference": "<InvokeAI image name>" }` or `{ "type": "path", "reference": "<absolute local path>" }`. `--image` and `--image-path` are exclusive. Denoising Strength must be finite with `0 < strength ≤ 1`, defaults to 0.75, and is invalid without a source.

All local validation precedes network access. A path source passes the `images upload` regular-file and image-content checks and has its dimensions read from its PNG, JPEG, or GIF header with the Go standard library. A WebP, BMP, or ICO path source returns `invalid_request` with guidance to use `images upload` and then an `image` source. Upscale path sources retain their existing behavior. After main-model resolution, family settings, components, and the live image-to-image invocation vocabulary are checked before source inspection or upload. An `image` source is then inspected; a missing image is `not_found`, and a contradictory name is `invalid_invokeai_response`. A path source is uploaded once immediately before enqueue. An inconclusive upload returns `outcome_unknown` with no enqueue. If the uploaded Image Reference dimensions differ from the locally read dimensions, Bediz returns `invalid_invokeai_response` with no enqueue. Every failure after a successful upload retains its error code, adds `source_image` and `source_uploaded: true`, and leaves the upload in InvokeAI.

Explicit paired width and height take precedence, and the source is resized to that exact size. Otherwise each source dimension is rounded down to the family alignment below. Profile dimensions do not become defaults when a source is present, while profile applicability validation remains in force. Either source dimension below the family alignment is `invalid_request` before upload or enqueue. A path source's dimensions come from the local header; an `image` source's from its Image Reference.

| Family | Alignment | Encoder | `denoising_start` | Metadata `generation_mode` |
| --- | --- | --- | --- | --- |
| SDXL | 8 | `i2l` | `1 − strength` | `sdxl_img2img` |
| Anima | 8 | `anima_i2l` | `1 − strength` | `anima_img2img` |
| FLUX.1 | 16 | `flux_vae_encode` | `1 − strength^0.2` | `flux_img2img` |

The SDXL graph keeps the text-to-image topology and noise at the resolved dimensions. It feeds the source directly to an intermediate `i2l` (`fp32: true`, `color_compensation: "None"`) when dimensions match, or through intermediate `img_resize` with bicubic resampling when they differ. The main loader's VAE, or the selected `vae_loader` override, feeds both `i2l` and `l2i`. `i2l` latents feed `denoise_latents.latents`; `denoising_start` is `1 − strength` and `denoising_end` is 1. `core_metadata` records `generation_mode: "sdxl_img2img"`, resolved `strength`, and `init_image` as the source image name. One non-retried `enqueue_batch` produces one queue item per resolved seed using the same source. Waiting ignores intermediate resize images and returns each item's single non-intermediate output.

The Anima graph keeps its tested text-to-image topology, including negative conditioning. The source feeds intermediate `anima_i2l` directly when dimensions match, or through intermediate `img_resize` with bicubic resampling when they differ. The `anima_model_loader` VAE feeds both `anima_i2l` and `anima_l2i`. Encoder latents feed `anima_denoise.latents`; `denoising_start` is `1 − strength`, `denoising_end` is 1, and `add_noise` is true. The denoiser uses the resolved dimensions. `core_metadata` records `generation_mode: "anima_img2img"`, resolved `strength`, and `init_image` as the source image name. One non-retried `enqueue_batch` produces one queue item per resolved seed using the same source. Waiting ignores intermediate resize images and returns each item's single non-intermediate output.

The FLUX.1 graph keeps its tested text-to-image topology. The source feeds intermediate `flux_vae_encode` directly when dimensions match, or through intermediate `img_resize` with bicubic resampling when they differ. The `flux_model_loader` VAE feeds both `flux_vae_encode` and `flux_vae_decode`. Encoder latents feed `flux_denoise.latents`; `denoising_start` is `1 − strength^0.2`, following InvokeAI 6.14.1's default optimized denoising, `denoising_end` is 1, and `add_noise` is true. For example, strength 0.75 resolves to approximately 0.05591249 and strength 0.5 to 0.12944944. The denoiser uses the resolved dimensions. `core_metadata` records `generation_mode: "flux_img2img"`, the public `strength`, and `init_image` as the source image name. Variant and format support matches text-to-image: `dev` or `schnell` in `checkpoint`, `bnb_quantized_nf4b`, or `gguf_quantized` format. Kontext dev and Krea dev models are accepted by their `dev` variant; no purpose is inferred from display names. `dev_fill`, unknown variants, SDNQ, and ordinary `diffusers` remain `unsupported_capability` before upload. Non-empty negative prompts and guidance for schnell remain `invalid_request`. One non-retried `enqueue_batch` produces one queue item per resolved seed using the same source. Waiting ignores intermediate resize images and returns each item's single non-intermediate output.

### 11.8 SDXL, Anima, and FLUX.1 LoRAs

`loras` is an optional, ordered, non-empty array of `{ "model": "<Model Key or unique name>", "weight": <number> }`; `weight` may be omitted. An empty array, explicit `null`, null element, unknown element member, empty selector, or non-finite or out-of-range explicit weight is `invalid_request` before network access. The permitted LoRA Weight range is −10 to 10, inclusive. A request without `loras` behaves as before, with unchanged graph and receipt. Generation Profiles exclude `loras`.

The repeatable convenience flag is `--lora <selector>[=<weight>]`; order is preserved and commas stay in the selector. It splits at the last `=`. A present suffix must be a finite decimal weight in range, and the selector must be non-empty. `--lora` cannot be mixed with `--request`.

After the main model resolves, each selector resolves by exact Model Key or unique name under the component-override rules. An ambiguous name returns `selection_required` with kind `lora` and Model Key-sorted candidates. An unknown name is `invalid_request`. A model whose type is not `lora` or whose base differs from the main model's `sdxl`, `anima`, or `flux` base is `unsupported_capability`; every LoRA format of the matching base is accepted. This rejects `flux2` LoRAs and `control_lora` models for FLUX.1. Two items resolving to the same Model Key are `invalid_request`. Omitted weight resolves to the model's `default_settings.weight` when present, otherwise 0.75. An out-of-range recorded default is `invalid_request` asking for an explicit weight. All resolution and compatibility checks precede source upload and enqueue.

In either SDXL Generation Mode, each LoRA adds one intermediate `sdxl_lora_loader` node with its complete Model Identifier and resolved weight. The first takes `sdxl_model_loader` outputs `unet`, `clip`, and `clip2`; each next loader takes the preceding loader's outputs. The final `unet` feeds `denoise_latents`, and its `clip` and `clip2` feed both `sdxl_compel_prompt` nodes. The VAE path and image-to-image encoder path remain unchanged. The chain applies LoRAs in request order; the stock frontend's `collect` branch orders them by random execution node IDs. `core_metadata.loras` records `{ "model": <complete Model Identifier>, "weight": <resolved weight> }` in request order. One `enqueue_batch` is sent and never retried after an inconclusive result.

In either Anima Generation Mode, each LoRA adds one intermediate `anima_lora_loader` node with its complete Model Identifier and resolved weight. The first takes `anima_model_loader` outputs `transformer` and `qwen3_encoder`; each next loader takes the preceding loader's outputs. The final `transformer` feeds `anima_denoise`, and its `qwen3_encoder` feeds both the positive and negative `anima_text_encoder` nodes. The negative conditioning branch, VAE path, and image-to-image encoder path remain unchanged. The chain applies LoRAs in request order. `core_metadata.loras` records the same ordered `{ "model": <complete Model Identifier>, "weight": <resolved weight> }` records. A request without LoRAs keeps its existing graph and receipt byte-for-byte unchanged.

In either FLUX.1 Generation Mode, dev and schnell each apply one intermediate `flux_lora_loader` per LoRA, in request order, with its complete Model Identifier and resolved weight. The first takes `flux_model_loader` outputs `transformer`, `clip`, and `t5_encoder`; each next takes the preceding loader's outputs. The final `transformer` feeds `flux_denoise`, and its `clip` and `t5_encoder` feed `flux_text_encoder`. The `max_seq_len` edge still comes directly from `flux_model_loader`, and the VAE and image-to-image encoder paths are unchanged. `core_metadata.loras` records the same ordered `{ "model": <complete Model Identifier>, "weight": <resolved weight> }` records. Main-model variant and format support, negative-prompt rejection, and schnell-guidance rejection are unchanged. LoRA-less graphs, fixtures, and receipts are unchanged.

## 12. Parameter Recall and UI synchronization

`bediz recall` submits a supported generation parameter patch to InvokeAI's Recall API without enqueueing generation. On stock InvokeAI 6.14.1, the Anima, SDXL, and FLUX.1 patch fields consumed by the frontend are the positive and negative prompts, exact main model, width and height together, steps, and seed. At least one supported field is required. Prompts and seed may be patched without a model; dimensions and steps require an explicit main model of a registered generation family so Bediz can validate their family-specific meaning. A schema-version-1 Recall Request Document and the matching convenience flags compile to the same typed operation. Unknown or inapplicable fields are errors.

The Recall Request Document contains `schema_version` and the optional `model`, `positive_prompt`, `negative_prompt`, `width`, `height`, `steps`, and `seed` fields. The corresponding flags are `--model`, `--prompt`, `--negative-prompt`, `--width`, `--height`, `--steps`, and `--seed`. Operation flags cannot be mixed with `--request`. Family-specific dimension alignment and step constraints apply after model resolution; stock InvokeAI 6.14.1's Recall API also requires both dimensions to be at least 64 pixels. Bediz rejects invalid Recall dimensions before posting. Successful machine output is one V1 Result Envelope with `operation: "recall"`, empty warnings, and data containing `queue_id: "default"` and `mode: "patch"`. Success means InvokeAI accepted the patch; it does not assert that a browser was open to receive the event. An inconclusive Recall mutation returns `outcome_unknown` without a retry.

Standalone `recall` checks the tested Recall endpoint, request body, and the common patch fields through the same Compatibility Check used by `doctor`. It does not require `cfg_scale`; `doctor` checks that additional SDXL field in its `recall` row to report UI Synchronization readiness (§10).

InvokeAI 6.14.1 resolves the Recall main model by display name and takes the first match. Bediz resolves the requested Model Key or unique name before Recall and submits its display name only when that name identifies the same single installed main model. An ambiguous input selector returns `selection_required`; a selected key whose display name collides with another main model returns `unsupported_capability`. Both fail before mutation. V1 does not offer `recall --replace`: the stock 6.14.1 frontend ignores the null scalar values sent by InvokeAI's strict Recall mode, so omitted scalar controls remain populated.

After a successful generation enqueue, Bediz attempts to patch the supported resolved fields by default, using the first output's resolved seed when there are multiple outputs. It does not retry the Recall mutation. Generation remains successful if Recall fails or exact model Recall is impossible; the result contains a structured `ui_sync_failed` warning. A successful partial synchronization carries a `ui_sync_partial` warning identifying the generation fields that the stock frontend cannot restore. The Execution Receipt always retains every resolved setting and output seed.

On stock InvokeAI 6.14.x:

- Anima generation synchronization is partial. The frontend Recall event handler maps prompts, model, dimensions, steps, and seed to UI state, but does not restore Anima scheduler, guidance, VAE, Qwen3 encoder, output count, or Output Board controls. The visible queue item, result image, metadata, and Execution Receipt remain available for Handoff.
- Anima image-to-image sends the same Recall patch as Anima text-to-image. Its `ui_sync_partial.not_restored` list appends `source_image` and `strength` after the six text-to-image fields. Automatic Recall does not restore either field.
- Until LoRA Recall support lands, an Anima generation with LoRAs appends `loras` after the existing text-to-image or image-to-image `ui_sync_partial.not_restored` fields; automatic Recall otherwise remains unchanged.
- SDXL generation synchronization is partial. Automatic Recall also patches `cfg_scale` from resolved guidance; live stock 6.14.1 frontend verification showed prompt, model, dimensions, steps, first seed, and CFG restored after model loading. It does not restore scheduler, VAE override, output count, or Output Board; the `ui_sync_partial.not_restored` list names those four fields. Standalone `recall` accepts SDXL main models, validates 8-pixel dimension alignment, and enforces the Recall API's 64-pixel minimum.
- SDXL image-to-image sends the same Recall patch as SDXL text-to-image, without `denoise_strength`. Its `ui_sync_partial.not_restored` list appends `source_image` and `strength` after the four text-to-image fields. The image metadata panel can recall the recorded strength separately; automatic Recall does not restore it.
- Until LoRA Recall support lands, an SDXL generation with LoRAs appends `loras` to `ui_sync_partial.not_restored`; automatic Recall otherwise remains unchanged.
- FLUX.1 generation synchronization is partial. Automatic Recall patches prompts, model, dimensions, steps, and the first seed. The `ui_sync_partial.not_restored` list names scheduler, guidance for dev only, VAE, T5 encoder, CLIP Embed, output count, and Output Board. Standalone `recall` accepts supported FLUX.1 main variants and formats, validates 16-pixel alignment, and enforces the Recall API's 64-pixel minimum.
- FLUX.1 image-to-image sends the same Recall patch as FLUX.1 text-to-image, without `denoise_strength`. Its `ui_sync_partial.not_restored` list appends `source_image` and `strength` after the variant-specific text-to-image fields. Automatic Recall does not restore either field.
- Until LoRA Recall support lands, a FLUX.1 generation with LoRAs appends `loras` after its variant-specific text-to-image or image-to-image `ui_sync_partial.not_restored` fields; automatic Recall otherwise remains unchanged.
- Generative upscale synchronization is partial for SDXL and SD1.5. After a successful upscale enqueue, including `--no-wait`, Bediz sends one Recall patch with the resolved positive and negative prompts, the exact main model under the display-name uniqueness rule above, steps, and the seed. The stock 6.14.1 Upscale tab shares these values with the Generate tab. The patch never contains width and height, which do not apply to the Upscale panel, or `cfg_scale`, which stock Recall writes to the Generate tab's CFG rather than the upscale CFG. The patch uses its own tested fields, not the generation family registry. A display-name collision, a missing Recall endpoint, an incompatible patch schema, or an inconclusive or rejected Recall adds `ui_sync_failed` and leaves the upscale outcome, its single enqueue, and its Execution Receipt unchanged. A failed or inconclusive enqueue sends no Recall. A successful patch adds `ui_sync_partial` whose `not_restored` list is `source_image`, `upscale_model`, `scale`, `creativity`, `structure`, `tile_controlnet`, `tile_size`, `tile_overlap`, `scheduler`, `guidance`, `vae`, and `board_id`.
- Standalone `recall` does not accept SD1.5 main models; SD1.5 is not a generation family in V1.

Partial upscale synchronization guarantees visible queue items, result images, embedded metadata, prompt, model, steps, and seed recall, and an exact Bediz execution receipt. It does not repopulate the source image, Spandrel model, scale, creativity, structure, Tile ControlNet, tile size, tile overlap, upscale scheduler, upscale CFG, VAE, or Output Board in the Upscale panel. When the recalled main model has a different base, the stock frontend's own model-change handling, not the Recall patch, replaces selections that are incompatible with the new base. Live 6.14.1 verification showed it selecting the first installed ControlNet of the new base whose name contains `tile`, and resetting an incompatible VAE to the default. This selection can differ from the Tile ControlNet and VAE Bediz used, so both stay in `not_restored`. Compatible Upscale panel controls are not reset.

Bediz will not manipulate browser storage or DOM state to simulate missing Recall fields. A later InvokeAI version may upgrade generation or upscale synchronization to full only after its API and frontend behavior have been tested. Live UI verification uses a browser to observe the Handoff result; the browser is not part of Bediz's control path.

## 13. Generative upscale

V1 `upscale` implements InvokeAI's tiled multi-diffusion upscale, not a standalone RealESRGAN resize.

V1 target main-model families:

- SD1.5
- SDXL

The operation resolves:

- Main model
- Spandrel image-to-image upscale model
- Compatible Tile ControlNet
- Optional VAE

The request may include positive and negative prompts, scale, creativity, structure, steps, scheduler, CFG scale, seed, tile size, tile overlap, optional VAE, and output board. LoRAs and additional post-processing models are deferred.

The current tested capability is SD1.5 and SDXL from an existing InvokeAI image or an absolute local image path. A local file is uploaded once, after every validation and resolution step, and the resulting Image Reference is recorded in the receipt. If anything fails after the upload, Bediz reports the uploaded source and never deletes it automatically.

### 13.1 Upscale Request Document

The canonical request has `schema_version: 1`, a required `source` object of the form `{"type":"image","reference":"<image name>"}` or `{"type":"path","reference":"<absolute local path>"}`, and a main-model `model` selector unless a named profile supplies one. It accepts these optional typed fields; absent fields take the listed defaults after profile values are applied. `components` is an object with only the named selectors. A `path` source names a file on the CLI machine, unlike a `models install` path, which names a path on the InvokeAI server.

| Request field | Flag | Valid values | Default |
| --- | --- | --- | --- |
| `source` | `--image` or `--image-path` | Existing InvokeAI image name, or absolute path to a readable regular file on the CLI machine | Required |
| `model` | `--model` | Exact main Model Key or unique name | Required unless the profile supplies one |
| `profile` | `--profile` | Local Generation Profile name with an `upscale` section | None |
| `positive_prompt` | `--prompt` | String | `""` |
| `negative_prompt` | `--negative-prompt` | String | `""` |
| `scale` | `--scale` | Integer 2, 4, or 8 | 4 |
| `creativity` | `--creativity` | Integer −10 through 10 | 0 |
| `structure` | `--structure` | Integer −10 through 10 | 0 |
| `steps` | `--steps` | Positive integer | 30 |
| `scheduler` | `--scheduler` | Scheduler from the SDXL list in §11.2, for either family | `kdpm_2` |
| `guidance` | `--guidance` | Finite CFG scale at least 1 | 2.0 |
| `seed` | `--seed` | Unsigned 32-bit integer | Random |
| `tile_size` | `--tile-size` | Multiple of 64 from 512 through 1536 | 1024 |
| `tile_overlap` | `--tile-overlap` | Multiple of 8 from 16 through 512, less than `tile_size` | 128 |
| `board_id` | `--board` | Exact Output Board identifier | Uncategorized |
| `components.upscale_model` | `--upscale-model` | Spandrel key or unique name | Automatic when exactly one is compatible |
| `components.tile_controlnet` | `--tile-controlnet` | ControlNet key or unique name with the main model's base | No automatic choice |
| `components.vae` | `--vae` | VAE key or unique name with the main model's base | Main model's bundled VAE |

Exactly one of `--image` and `--image-path` is required; both or neither is `invalid_request`. Operation flags cannot be combined with `--request`, and the Request Document follows the §8.1 rules for unknown, repeated, and explicit `null` members. The command waits by default; `--no-wait` returns after acceptance, and `--timeout` bounds only local waiting. Every locally checkable bound, schema and source shape, and explicit empty selector is rejected before a network request. A `path` source must be absolute and name a readable regular file whose content passes the same image-type check as `images upload` (§15.1); a failure returns `invalid_request` before any network request. Bediz loads a named profile before any InvokeAI request. A missing profile returns `not_found`; a profile without an `upscale` section, or a request with no main model in either place, returns `invalid_request`, all before network access.

### 13.2 Resolution and execution

After local validation, Bediz checks the supported InvokeAI version; resolves the main model by exact key or unique name; accepts only an `sd-1` or `sdxl` main model with variant `normal`, which selects the upscale family; resolves components; verifies the live OpenAPI invocation vocabulary; and then confirms the source. An explicit request model wins over the profile model. For each upscale setting, an explicit request value wins over the profile's `upscale` value, which wins over the §13.1 default. Both supported families use the same settings, so every saved upscale setting is applicable to either supported family. Combined settings, including tile overlap relative to tile size, are validated after precedence is applied and before upload or enqueue. An `image` source is read with image inspection. A missing image returns `not_found` before enqueue; a returned Image Reference with a different image name returns `invalid_invokeai_response` before enqueue. Ambiguous main names return `selection_required` with candidates sorted by Model Key.

A `path` source is uploaded only after every step above succeeds, immediately before the enqueue, so an invalid or unresolvable request never leaves an uploaded image. The upload follows `images upload`: a non-intermediate user image without resizing, injected metadata, or a board. It is sent once and never retried. An inconclusive upload, including a response without an image name, returns `outcome_unknown` and nothing is enqueued; a conclusive rejection returns `invokeai_operation_failed`. After a successful upload, every later failure keeps its own error code and adds `source_image`, the complete uploaded Image Reference, and `source_uploaded: true` to its structured details. This covers enqueue rejection, an inconclusive or malformed enqueue response, a malformed or unknown-status queue response, a failed or canceled item, `scale_not_applied`, `wait_timeout`, and `interrupted`. Bediz never deletes the uploaded image.

The Spandrel model must have base `any` and type `spandrel_image_to_image`. An explicit compatible selector wins; otherwise a compatible profile preference is used; otherwise exactly one compatible installed model is chosen. Several return `selection_required` with kind `upscale_model`, and none returns `missing_component` with `RealESRGAN_x4plus` starter guidance. InvokeAI records no Spandrel scale, so completion dimensions are verified after waiting.

The Tile ControlNet must have the main model's base and type `controlnet`. An explicit compatible selector or a compatible profile preference is the caller's Tile choice. Without one, Bediz returns `selection_required` with kind `tile_controlnet` and every compatible ControlNet as sorted candidates, even if there is only one. With none installed, it returns `missing_component` with starter guidance for that base: `xinsir/controlNet-tile-sdxl-1.0` for SDXL and `lllyasviel/control_v11f1e_sd15_tile` for SD1.5. Bediz never infers Tile purpose from a name. The optional VAE override must have the main model's base and type `vae`; without an explicit selector or compatible profile preference the main model's bundled VAE is used. An explicitly selected component with the wrong base or type, including an SDXL ControlNet or VAE for an SD1.5 main model or the reverse, returns `unsupported_capability`. SD1.5 remains unsupported for `generate` and standalone `recall`.

Each profile component preference resolves by exact key or unique name to one installed model with the required base and type. An explicit request component selector wins without consulting that preference. An incompatible, ambiguous, or absent preference is skipped with `profile_preference_skipped`, carrying `profile`, `component`, and `reason` (`incompatible`, `ambiguous`, or `not_found`) in its details. Ordinary §13.2 component resolution then applies. The warning appears in the failure Result Envelope if fallback component resolution or another later step fails before an accepted enqueue, including compatibility checks, Source Image validation or upload, compilation, and enqueue rejection or an inconclusive result. When execution succeeds, it appears in both the Result Envelope and Execution Receipt. An upload response with an image name whose image or thumbnail URL cannot be normalized reports the retained Source Image but omits profile preference warnings; failures after an accepted enqueue also omit them. A skipped Tile preference never authorizes an automatic Tile choice.

The tested InvokeAI 6.14.1 batch uses Spandrel autoscale with `fit_to_multiple_of_8: true`, unsharp mask radius 2 and strength 60, tiled image-to-latents and latents-to-image with `fp32: true`, and tiled multi-diffusion denoising. Denoising start is `(10 − creativity) × 4.99 / 100`; denoising end is 1. Two Tile ControlNet nodes on the sharpened image use `balanced` control and `just_resize`. The first has weight `(structure + 10) × 0.0325 + 0.3`, begins at 0, and ends at `(structure + 10) × 0.025 + 0.3`. The second has weight `((structure + 10) × 0.0325 + 0.15) × 0.45`, begins where the first ends, and ends at 0.85. The SDXL branch uses `sdxl_model_loader` and positive and negative `sdxl_compel_prompt` nodes, each with its prompt also connected as style. The SD1.5 branch uses `main_model_loader`, whose CLIP passes through one `clip_skip` node with 0 skipped layers to positive and negative `compel` nodes; it has no style prompts, and clip skip is not a public setting. In both branches the main loader supplies the denoiser's UNet and the bundled VAE. An optional `vae_loader` replaces the main loader's VAE for both tiled transforms. The non-intermediate output carries the optional board and `core_metadata` with the source, scale, prompts, seed, expected dimensions, steps, scheduler, guidance, main and optional VAE model, Spandrel model, creativity, structure, and tile settings. The graph omits LoRAs and post-processing.

One upscale submits one batch with one resolved seed through one `enqueue_batch` mutation to the default queue. It is never retried. An inconclusive result is `outcome_unknown`. Waiting and queue item verification follow §11.5–11.6, including `pending_item_ids` in `wait_timeout` and `interrupted` details, selecting the single non-intermediate output image while ignoring the Spandrel and unsharp-mask intermediate image results. Zero or several final images, or a failed or canceled item, never produce a success receipt.

The expected output width is `floor(source_width × scale / 8) × 8`, and the expected height follows the same rule. For example, 513 × 513 at scale 2 expects 1024 × 1024. The source dimensions come from the inspected Image Reference for an `image` source and from the upload result for a `path` source. A completed output with different dimensions returns `invokeai_operation_failed` (exit status 6) with `reason: "scale_not_applied"`, expected and actual dimensions, queue identifiers, output Image Reference, and source Image Reference. `--no-wait` reports the expected dimensions without verifying output.

### 13.3 Upscale Execution Receipt

The V1 result envelope has `operation: "upscale"`. Its data contains `submitted_request` before profile values and defaults, including `profile` when named; the `source_image` Image Reference and `source_uploaded`, which is `true` only when Bediz uploaded a `path` source in this request; `resolved_settings` with the named `profile` when present, resolved prompts, scale, creativity, structure, steps, scheduler, guidance, tile size, tile overlap, expected `output_width` and `output_height`, optional `board_id`, exact `model_key`, `component_keys`, and one-element `seeds`; `queue` with queue, batch, and one item identifier; `outputs` with the verified item, seed, and Image Reference or an empty array for `--no-wait`; and `warnings` with profile preference warnings and the UI Synchronization warning described in §12. Receipt and Result Envelope warnings match.

## 14. Model management

Supported install sources are:

- InvokeAI starter model identifier
- Hugging Face reference
- Direct URL
- Local server path
- Civitai model-version page or identifier resolved to a direct artifact

### 14.1 Installation requests

An Installation Request Document requires `schema_version: 1` and a `source` with typed `type` (`starter`, `huggingface`, `url`, `path`, or `civitai`) and `reference`. Matching source flags (`--source-type` and `--source`) compile to the same operation; operation flags are not mixed with `--request`. An exact Civitai file may additionally use a positive integer `source.file_id`; a Hugging Face repository may use `source.artifact` (flag `--artifact`) to choose an exact artifact URL; a server path may use the operation's `move` setting. Unknown and inapplicable fields are errors.

Installation uses InvokeAI's tested generic POST job endpoint exactly once per submitted job; the Hugging Face-specific GET installation route is not used because it mutates state without returning an inspectable job. Install and authentication mutations require a tested InvokeAI version; compatible read-only status may operate on other versions. An inconclusive submission returns `outcome_unknown`, which directs callers to inspect the current model inventory and install job list before another submission; it is never replayed automatically.

A successful install returns accepted job identifiers, statuses, source types, and roles in the V1 Result Envelope's `data` without echoing source references, for example `{"jobs":[{"job_id":0,"status":"waiting","source_type":"url","role":"requested"}]}`. The actual job ID and status come from InvokeAI. Raw backend source, token, error text, and traceback are not returned.

`doctor` registers installation only when the tested generic POST endpoint advertises a required `source` query parameter and a JSON `201` response containing a `ModelInstallJob`. Bediz does not guess dependencies for arbitrary Hugging Face, URL, path, or Civitai artifacts; `doctor` reports missing required components and advertises starter installation separately only when the tested catalog and generic job endpoints are present.

The generic `models.install` row retains those requirements. Source-specific rows add requirements to the generic row: `family: "starter"` requires the tested starter catalog endpoint and response; `family: "huggingface"` requires `GET /api/v2/models/hugging_face`; `family: "path"` requires the generic POST's `inplace` query parameter; and `family: "source_token"` requires its `access_token` query parameter whenever a Source Token is supplied. One install call checks the generic row and every applicable source row before mutation. The additional failures are `missing_endpoint:GET /api/v2/models/hugging_face`, `incompatible_install_schema:inplace`, and `incompatible_install_schema:access_token`. A starter catalog entry that resolves to a Hugging Face repository also checks the Hugging Face row before submitting jobs.

### 14.2 Direct URL sources

`models install --source-type url --source URL` or a Request Document such as `{"schema_version":1,"source":{"type":"url","reference":"https://example.org/model.safetensors"}}` installs one artifact. User-supplied direct artifact URLs must be HTTP(S) without userinfo, query, or fragment; any of those fails validation before installation. Bediz never echoes a source URL or forwards an artifact URL containing embedded credentials.

### 14.3 Hugging Face sources

`models install --source-type huggingface --source org/repo` or the matching Request Document installs from a Hugging Face repository. A canonical `https://huggingface.co/org/repo` reference is equivalent. Bediz converts both forms to that exact HTTPS URL before calling the generic POST installer, avoiding InvokeAI's `org/repo` server-path collision. Variant, subfolder, file, query, and fragment reference forms are unsupported until tested; a user-supplied `huggingface` source with `::` is `invalid_request`.

Bediz asks the anonymous Hugging Face repository metadata API whether the exact repository is public or gated; no token is sent to that API. A denied or absent anonymous result is treated as potentially protected. If public access cannot be checked, Bediz fails before mutation rather than assuming the repository is public. Bediz then checks InvokeAI's read-only repository metadata for installable files. A Diffusers repository is treated as one package. A repository without a supported artifact fails before mutation.

The `models.install` row with `family: "huggingface"` checks that InvokeAI exposes the read-only repository metadata endpoint in addition to the generic install requirements (§14.1).

Multiple checkpoint artifacts return `selection_required` with `kind: huggingface_artifact`, the canonical repository URL as `selector`, and exact artifact URL candidates sorted by URL; no job is submitted. The caller resubmits the same `huggingface` source with a chosen candidate key as `source.artifact`. That request passes the same public-access and protected-repository checks as the initial request, then succeeds only when InvokeAI's current repository metadata still lists that exact URL; Bediz submits the artifact URL itself. Any other artifact, a Diffusers repository, or `artifact` on another source type fails as `invalid_request` before mutation.

### 14.4 Starter models

A starter is selected by its exact `source` identifier, not by a potentially duplicated display name. Starter-model dependencies declared in InvokeAI's returned catalog are submitted in catalog order before the selected starter as separately observable jobs. The starter result has `jobs` and `skipped` arrays. Jobs contain the accepted `job_id`, normalized `status`, `source_type: starter`, `role` (`dependency` or `starter`), and zero-based `dependency_index` for a dependency. Entries present in the catalog and marked installed are reported in `skipped` with the same role and index and `reason: already_installed`, before source normalization; unsupported installed source forms do not block the request. If every returned entry is installed, `jobs` is empty. InvokeAI 6.14.1 omits installed dependencies from the returned dependency list, so Bediz cannot identify or report those omitted entries; dependency indexes refer to the returned list.

Bediz preflights every entry it would install and returns `unsupported_capability` before any mutation if a source form or required protected-repository authentication input is unsupported. A starter source or dependency that needs installation and has an unsupported reference form fails before any job is submitted. An exact Hugging Face `/resolve/` artifact entry receives the same anonymous public-access check as its repository; when that repository is not verifiably public, the request requires `--token-stdin`. It does not require an InvokeAI login because Bediz reads no repository metadata for an exact artifact. A single `--token-stdin` value is sent only when all entries to install have the same URL origin; a mixed-origin starter request with a source token fails as `unsupported_capability` before mutation.

A partial rejected submission returns `invokeai_operation_failed` with accepted `jobs`, `skipped`, the rejected role/index, and HTTP status when available. An inconclusive submission returns `outcome_unknown` with accepted `jobs`, `skipped`, and the uncertain role/index. Neither is replayed automatically; a concurrent 409 is a conclusive conflict requiring reinspection.

A starter catalog source or dependency may use the single-subfolder `org/repo::path` form. Bediz validates the plain repository ID and a non-empty relative path without a leading slash, empty or dot segment, backslash, colon, or `+` multi-subfolder separator. Before any mutation, it finds that exact path in its parent folder through Hugging Face's anonymous tree API, following parent pagination. An entry of type `file` exists; an entry of type `directory` exists only if its first recursive tree page contains a file. Missing, empty, denied, malformed, or failed tree responses are `unsupported_capability`. This check does not use InvokeAI repository metadata because tested Diffusers-layout repositories can return `urls: null`. Bediz separately checks anonymous repository access. A repository that is not verifiably public requires InvokeAI's stored Hugging Face login to report `valid` through `auth huggingface status`; Bediz does not read or send that token. `--token-stdin` with any subfolder entry needing installation is `unsupported_capability` before mutation. Bediz submits each exact catalog string once to the tested generic POST installer, preserving dependency order and the usual skip and partial-failure semantics. There is no canonical HTTPS URL replacement for a subfolder. InvokeAI 6.14.1 checks for a server-local path with the same string before treating it as a Hugging Face source; Bediz accepts that residual server-path collision risk. Variant and multi-subfolder catalog sources remain unsupported.

### 14.5 Server path sources

`models install --source-type path --source PATH` and the matching Request Document `{"schema_version":1,"source":{"type":"path","reference":"PATH"}}` require an exact absolute path in the InvokeAI server's filesystem namespace. Bediz does not resolve or inspect that path on the CLI machine. The optional top-level boolean `move` applies only to path sources; omitted or false means in-place registration. Bediz sends `inplace=true` explicitly because InvokeAI 6.14.1 defaults that parameter to false. A true `move` requires Execution Approval `--yes`, including when the request comes from a document; `--yes` alone does not request a move and is not a document field. An approved move sends `inplace=false` and places the source file in InvokeAI-managed storage. A missing tested `inplace` endpoint parameter fails before mutation. Source tokens do not apply to paths. On the tested 6.14.1 installation, completed in-place registration left the source file at its original absolute path, while completed move removed that source file and placed it in the managed model directory. Both modes return one inspectable install job.

The `models.install` row with `family: "path"` reports a missing `inplace` parameter as `incompatible_install_schema:inplace` (§14.1).

### 14.6 Civitai resolution

Civitai support is deterministic source normalization, not model discovery.

- A direct download URL follows the generic URL validation rules in §14.2.
- A positive decimal version identifier or model page URL with an explicit positive `modelVersionId` is resolved through Civitai's model-version metadata. Civitai page URLs may carry only that `modelVersionId` selector.
- A model page's model ID must match the parent model ID in the exact version metadata. Metadata download URLs must have the canonical Civitai version or file shape; Bediz constructs the file URL from verified IDs instead of forwarding metadata URLs.
- A version with one file selects it. When several files exist, exactly one metadata-marked primary file may be selected. Otherwise `selection_required` returns numeric file IDs and names; the caller can resubmit an exact `file_id` belonging to that version.
- A model page URL (`https://civitai.com/models/{model_id}` with an optional slug segment and no query) never defaults to the newest or first version. Bediz reads Civitai's model metadata, verifies its model ID, and returns `selection_required` with `kind: civitai_version`, the numeric model ID as `selector`, and candidates sorted by numeric version ID, each with integer `id` and `name`, even if there is only one version. No installation is submitted. The caller resubmits a chosen ID as an exact version `source.reference`; `file_id` is invalid without an exact version.

After validating that the selected file belongs to the exact version, Bediz constructs the artifact URL as `https://civitai.com/api/download/models/{version_id}?fileId={file_id}` using verified positive decimal IDs. No other host, path, query key, userinfo, or fragment is allowed for this internally resolved URL; unsupported metadata URL forms fail before mutation.

Bediz provides no Civitai search, ranking, recommendation, or content-policy layer in V1. The creative agent may use its browser to discover a model and then pass the selected reference to Bediz.

### 14.7 Source tokens

Protected generic URLs and Civitai downloads accept a token through `--token-stdin`. For URL installation, the flag works with source flags or a Request Document read from a file; an empty standard-input token fails before mutation. `--request -` and `--token-stdin` cannot be used together because both consume standard input. Bediz does not persist the token; it never appears in a Request Document, local configuration, receipt, result, or diagnostic.

For a Civitai source, Bediz sends the supplied token as a Bearer header only to Civitai's HTTPS model or version metadata endpoint, without following redirects. Before a protected install mutation, Bediz verifies that the tested generic endpoint advertises the `access_token` query parameter. InvokeAI 6.14.1 receives the token in that parameter and stores it in a plaintext temporary install marker while a remote download runs. Bediz omits the complete token-bearing request URL and backend response text from failures, and refuses redirects for that request. Normal terminal handling removes the marker; a paused or interrupted install can retain it for resumption. InvokeAI or proxy access logs are outside Bediz's secrecy guarantee.

The `models.install` row with `family: "source_token"` reports a missing `access_token` parameter as `incompatible_install_schema:access_token` for every source type that accepts a Source Token (§14.1).

Bediz rejects token-bearing installation and Hugging Face login over a non-loopback plain-HTTP InvokeAI target. With a source token, each artifact URL must also use HTTPS or a loopback host (`localhost` or a loopback IP address); a non-loopback plain-HTTP artifact returns `invalid_request` for a direct URL or `unsupported_capability` for a starter catalog entry, before any install mutation.

On the tested InvokeAI 6.14.1 baseline, a protected direct Hugging Face repository request requires a valid InvokeAI Hugging Face login for metadata access and a separate `--token-stdin` source token for its file downloads; Bediz never reads back the stored login token. If either prerequisite is unavailable, a direct Hugging Face request returns `authentication_failed` and a starter entry using a plain repository URL returns `unsupported_capability` before installation. Protected starter subfolder entries instead use only InvokeAI's valid stored login, as described in §14.4.

### 14.8 Hugging Face authentication

Hugging Face authentication uses InvokeAI's token support through `bediz auth huggingface`. Bediz does not maintain its own token store.

`auth huggingface status` reads InvokeAI's `GET /api/v2/models/hf_login` and returns `data.status` as exactly `valid`, `invalid`, or `unknown`. The status reports InvokeAI's verification result; `unknown` is a successful status inspection but does not establish whether a usable token exists. The command never returns the token. Compatible read-only status may run on an untested InvokeAI version when the endpoint is present. `doctor` registers status against the GET endpoint and registers login and logout only for the tested version range with the POST and DELETE methods respectively.

`auth huggingface login --token-stdin` reads a non-empty token from standard input, sends it once as the JSON `token` field to InvokeAI's `POST /api/v2/models/hf_login`, and reports `data.status: "valid"` only when InvokeAI verifies it. An `invalid` response is `authentication_failed` (exit 5); an `unknown` response, malformed successful response, or inconclusive transport result is `outcome_unknown` (exit 6), requiring a new status inspection before another mutation. `auth huggingface logout` sends one `DELETE` to the same endpoint and reports `data.status: "invalid"` when InvokeAI confirms removal. A `valid` response is `invokeai_operation_failed` (exit 6); `unknown`, malformed success, or inconclusive transport returns `outcome_unknown` (exit 6). Conclusive HTTP rejection follows the standard structured error and exit mapping. Neither mutation retries or follows redirects. Both commands return exactly one V1 Result Envelope with `--json`, and human output otherwise; status, success, failure, diagnostics, and receipts never contain the Hugging Face token.

Login checks the recorded `auth.huggingface.login` endpoint and token request body through the same Compatibility Check used by `doctor` before sending the token.

### 14.9 Installation job status

`models status --job-id 0` and `{"schema_version":1,"job_id":0}` inspect the job currently held under that exact non-negative integer ID, including zero. The `data` projection contains `job_id`, normalized `status`, optional `bytes` and `total_bytes`, and `model_key` only when a completed backend record supplies one. The projection excludes backend source, credentials, error text, and traceback. `doctor` registers status as compatible read-only inspection.

The tested InvokeAI install states are `waiting`, `downloading`, `downloads_done`, `running`, `paused`, `completed`, `error`, and `cancelled`. A status outside that set fails as `invalid_invokeai_response`; Bediz does not guess whether the job finished. A job no longer retained by InvokeAI returns `not_found`, not an inferred success.

InvokeAI 6.14.1 scopes these IDs to its current install-job registry: after a server restart, an ID can disappear or identify a different job. Bediz does not treat an old ID as a durable installation receipt; callers inspect the current model inventory and job list before acting on an uncertain outcome.

### 14.10 Local scan

`models scan --path SERVER_PATH` and `{"schema_version":1,"path":"SERVER_PATH"}` inspect an absolute folder path in the InvokeAI server's filesystem namespace, using the read-only `GET /api/v2/models/scan_folder` endpoint with its `scan_path` query parameter. Bediz accepts POSIX and Windows absolute server path syntax, as with `models install` path sources; it never inspects that path on the CLI machine. A missing or relative path is `invalid_request` (exit 2). InvokeAI 6.14.1 rejects an invalid folder with HTTP 400, which Bediz reports as a conclusive `invokeai_operation_failed` (exit 6); other HTTP statuses follow the standard error mapping. The V1 Result Envelope has `operation: "models.scan"` and data shaped as `{"models":[{"path":"/server/model.safetensors","installed":true}]}`. It maps InvokeAI's `is_installed` to `installed`, sorts entries by path, and includes no other backend fields. A missing installed state in a successful backend response is `invalid_invokeai_response`. Scanning installs and moves nothing. `doctor` registers it as compatible read-only inspection when the GET endpoint exists, including on an untested InvokeAI version.

### 14.11 Deletion

`models delete MODEL_KEY --yes`, or a Request Document `{"schema_version":1,"model_key":"MODEL_KEY"}` plus `--yes`, removes one installed model. The selector is an exact Model Key only; because the operation is destructive, a display name or any other selector is never resolved, and a value that is not a current key returns `not_found` (exit 6) without a mutation. The key must be one path segment: keys containing `/`, `\`, or `%`, and the complete keys `.` and `..`, are rejected before URL resolution. V1 has no bulk deletion, and InvokeAI's bulk endpoint is not used. `--yes` is Execution Approval, never a Request Document field, and is required for either input form. A missing or path-like key, missing approval, unknown field, or unsupported request schema version is an invalid local request with exit status 2 before any network request.

Deletion requires an InvokeAI version in the supported range. Bediz then reads the model with `GET /api/v2/models/i/{key}`; an absent key returns `not_found` and a record for another key or without a name, base, type, or format returns `invalid_invokeai_response`, both without a mutation. It sends `DELETE /api/v2/models/i/{key}` once and never retries it. The V1 Result Envelope has `operation: "models.delete"` and data holding the summary the model had before deletion: `{"key": ..., "name": ..., "base": ..., "type": ..., "format": ...}`. A model removed between the read and the deletion returns `not_found`; another conclusive rejection, including InvokeAI's 409 for an operation already in progress on that model, returns `invokeai_operation_failed`. A lost response or gateway status returns `outcome_unknown` with exit status 6, and the caller inspects `models list` before deciding whether to submit another deletion.

Deleting a managed model removes its files; deleting an in-place registration unregisters it without deleting the source. On the tested 6.14.1 installation, deleting a model whose files InvokeAI manages removed its files and key directory from the models directory, while deleting an in-place registration removed only the record and left the source file at its original path. Deleting one model removed no other model. `doctor` registers deletion only for the tested version range with the GET and DELETE methods of that endpoint.

## 15. Images, queues, and boards

Image operations use stable InvokeAI image names rather than gallery positions. Upload accepts local files; download writes an explicitly selected image; deletion requires `--yes`.

Queue operations expose InvokeAI batch and item identifiers. Waiting has no total timeout by default; callers may supply `--timeout`. `queue cancel` is explicit and does not require a second confirmation. `queue clear` requires `--yes`.

An output board is optional. With no board identifier, InvokeAI displays the image as Uncategorized. Bediz never inherits the board currently selected in a browser. `boards list`, `boards get`, and `boards create` are supported. Board deletion is deferred until its effect on contained images has a separate destructive-operation contract.

### 15.1 Inspection and upload operations

The image and queue commands are `images list`, `images get`, `images upload`, `images download`, and `images delete`, and `queue list`, `queue get`, `queue wait`, `queue cancel`, and `queue clear`. `models list` is specified here with them; the other model commands are in §14.

Each operation accepts a typed request document with `schema_version: 1`. Convenience flags and positional arguments compile to the same request values. Operation inputs cannot be combined with `--request`.

`models list` accepts optional exact `base_models`, `model_type`, `model_format`, and `model_name` filters. Its result is sorted by model name and then model key. A model summary contains the stable model key, name, base, type, format, optional size in bytes, and optional description. It also contains `trigger_phrases`, an array of strings sorted in ascending order, for any model whose InvokeAI record has a non-empty set; absent, null, and empty sets omit the member. For models of type `lora`, a recorded, non-null `default_settings.weight` is reported as the numeric `default_weight`, including zero and negative values. The member is omitted for other model types or when the weight or default settings are absent or null; no fallback weight is supplied in inventory results. Human output shows the recorded trigger phrases and default weight when present, while lines without either remain unchanged. Existing members and filters are unchanged. Bediz does not expose model filesystem paths, hashes, source API responses, or source URLs in this result.

`images list` accepts `offset`, `limit`, optional `board_id`, and `include_intermediate`. The defaults are offset zero, limit twenty, and no intermediate images. Limits below one or above one hundred are invalid local requests and return exit status 2. Results are newest first. `images get` requires one exact InvokeAI image name. Image results contain an Image Reference with the stable image name, dimensions, origin, category, timestamps, intermediate and starred status, optional board, session and node identifiers, workflow availability, and absolute full-image and thumbnail URLs.

`images upload` requires an absolute local file path. Before any network request, including version inspection, Bediz validates that the path names a readable regular file and that Go's HTTP content-type detection identifies its first 512 bytes (or the entire file when shorter) as `image/*`. An empty file or content without a recognized image signature returns `invalid_request` with exit status 2. The file extension never substitutes for this content check; a recognized image with an unrelated extension still uses its detected image media type. InvokeAI decodes the full image. Bediz uploads the file as a non-intermediate user image without resizing, injected metadata, or an implicit board. The upload is sent once and never retried; an inconclusive transport result or a response without an image name is `outcome_unknown`. A successful result contains the uploaded Image Reference. Upload is available only when the InvokeAI version is in the supported range.

`images download IMAGE_NAME --output PATH`, or a Request Document with `image_name` and `output`, saves the full-resolution image to a new file on the CLI machine. Both fields are required; the image name is exact. A relative output path resolves against the working directory. V1 has no `--replace`, and `replace` is an unknown field. Before any network request, Bediz requires the output's parent to be an existing directory and nothing to exist at the output path, including a directory or a dangling symbolic link; a missing output, a missing or non-directory parent, or an unsupported schema version is an invalid local request with exit status 2. An existing target returns `invalid_request` with `reason: "output_exists"` and the absolute `path`. Bediz reads `GET /api/v1/images/i/{image_name}/full` as a safe read that may be retried within the configured limit, writes the body to a temporary file in the target directory, and publishes it, with mode 0644 where the platform has POSIX permissions, through a hard link, a create-exclusive operation that fails when the target exists. A rename is never used because it replaces an existing target. When the target appears between the pre-check and publishing, the result is the same `output_exists` failure and the file at the target is left untouched. The temporary file is removed on every path, so a failure leaves no file at the target. An absent image returns `not_found` with exit status 6. A response that is not an `image/*` media type, or whose body cannot be read completely, returns `invalid_invokeai_response`. The download limit is 256 MiB, separate from the HTTP response-size limit for JSON responses, because the body streams to disk instead of memory; it admits an 8192 × 8192 image at four bytes per pixel. A larger body returns `invalid_invokeai_response` with `reason: "response_too_large"` and `limit_bytes`. `--timeout` bounds the whole request, including reading the body, and may accompany `--request`; a large image over a slow link to a remote InvokeAI may need a larger value. A local file-system failure, including a file system without hard links, returns `output_write_failed` with exit status 6 and the absolute `path`. The result is `{"image_name": ..., "path": ..., "size_bytes": ..., "content_type": ...}`, where `path` is the absolute written path and `content_type` is the media type InvokeAI reported. Download sends no mutation and may run on an untested but compatible InvokeAI version.

`images delete IMAGE_NAME --yes`, or a Request Document with one exact `image_name` plus `--yes`, deletes only the named gallery image through `DELETE /api/v1/images/i/{image_name}`. V1 has no name pattern, board-wide, or multi-image selector. The image name must be one path segment: names containing `/`, `\`, or `%`, and the complete names `.` and `..`, are rejected before URL resolution, which could otherwise redirect a deletion to another image or a bulk endpoint. `--yes` is Execution Approval, never a Request Document field, and is required for either input form. A missing or path-like name, missing approval, unknown field, or unsupported request schema version is an invalid local request with exit status 2 before any network request. Deletion requires an InvokeAI version in the supported range. Bediz sends the deletion once, never retries it, and returns `{"image_name": ...}` only when InvokeAI confirms exactly that image in `deleted_images` and reports no failed images. An absent image returns `not_found` with exit status 6; a conclusive rejection returns `invokeai_operation_failed`. A lost response, gateway status, malformed response, or success response that does not confirm only the named image returns `outcome_unknown` with exit status 6. The caller inspects the gallery before deciding whether to submit another deletion.

`queue list` accepts a queue identifier, offset, and limit. The queue identifier defaults to `default`, offset defaults to zero, and limit defaults to twenty. Limits below one or above one hundred are invalid local requests and return exit status 2. Results are newest first and contain lightweight queue-item summaries rather than execution graphs. `queue get` requires an item identifier and returns normalized identifiers, status, priority, origin, destination, timestamps, a concise error when present, and Image References for completed image outputs when available. Bediz does not expose raw execution graphs or server tracebacks.

`queue wait ITEM_ID...`, or a Request Document with `queue_id` (default `default`) and `item_ids`, observes queue items until each reaches a terminal status. `item_ids` is a non-empty list of positive integers without duplicates; the positional arguments compile to it. A zero, negative, non-integer, or repeated identifier is an invalid local request and returns exit status 2 before any network request. Waiting polls `queue get` inspection with the intervals and tested status set of §11.5: `pending`, `in_progress`, and `waiting` are non-terminal; `completed`, `failed`, and `canceled` are terminal. Each round polls, in request order, only the items not yet observed as terminal. A status outside the tested set returns `invalid_invokeai_response` with the `queue_id`, the requested `item_ids`, and the `item_id` and `status` it concerns; an item that reports another item or queue identity is also `invalid_invokeai_response`. `queue wait` checks no batch identity. An absent item returns `not_found` with exit status 6. The result is `{"queue_id": ..., "items": [...]}`, holding each item's `queue get` projection in request order. A failed or canceled item is data, not an operation error: the wait succeeds with exit status 0, and the item carries its concise error when InvokeAI reports one. Waiting has no total timeout by default. `--timeout` bounds only the local wait and may accompany `--request`; when it elapses, Bediz returns `wait_timeout` with `queue_id`, the requested `item_ids`, and `pending_item_ids`, the items not yet terminal in request order. Local interruption returns `interrupted` with exit status 130 and the same details. `queue wait` sends no mutation: neither a timeout nor an interruption cancels anything remotely, and it never enqueues or cancels an item. Like `queue get`, it may run on an untested but compatible InvokeAI version.

`queue cancel ITEM_ID`, or a Request Document with `queue_id` (default `default`) and `item_id`, sends one cancellation for that item. The item identifier must be a positive integer, as for `queue get`; a zero, negative, or non-integer identifier is an invalid local request and returns exit status 2 before any network request. V1 has no batch or bulk cancel selector; batch cancellation is deferred. Cancellation requires an InvokeAI version in the supported range and no `--yes`. InvokeAI 6.14.1 cancels the non-terminal items (`pending`, `in_progress`, and `waiting`) in the named item's Workflow-Call Chain, the named item included, and leaves completed, failed, and already canceled items unchanged. Bediz documents that effect and does not narrow it. Bediz's own generate and upscale batches create no Workflow-Call Chains, so for them at most the named item is canceled. Canceling an item that is already terminal is not an error: the operation succeeds with exit status 0 and reports the item's unchanged status. The result is `{"item": ...}`, the `queue get` projection of the named item as InvokeAI returns it after the cancellation. An absent item returns `not_found` with exit status 6. The cancellation is sent once and never retried. An inconclusive transport result, or a success response that does not name the requested item and queue, returns `outcome_unknown`, and the caller inspects `queue get` before trying again. A conclusive InvokeAI rejection returns `invokeai_operation_failed`. When InvokeAI answers the cancellation with the named item but reading the item's Image References then fails, the cancellation was applied: the failure keeps its own error code and adds `cancel_applied: true`, `queue_id`, `item_id`, and `item_status`, the status InvokeAI returned, to its structured details. The caller inspects `queue get` instead of canceling again.

`queue clear --yes`, or a Request Document with `queue_id` (default `default`), sends one clear request for that queue to `PUT /api/v1/queue/{queue_id}/clear`. The operation is irreversible. `--yes` is execution approval and is not a Request Document field: it is required even when the request comes from a document, and a missing `--yes` is an invalid local request that returns exit status 2 before any network request. Clearing requires an InvokeAI version in the supported range. InvokeAI decides the scope, and Bediz neither widens nor narrows it: an admin caller, including the single-user default, cancels and deletes every item in the queue, and any other caller cancels and deletes only their own items. On InvokeAI 6.14.1 in single-user mode, a clear of a queue holding one completed, one `in_progress`, and one `pending` item deleted all three: the in-progress item stopped executing, and none of the three could be read afterwards with `queue get`. Items in other queues were unchanged. The result is `{"queue_id": ..., "deleted": ...}`, where `deleted` is the count InvokeAI reports. The clear is sent once and never retried. An inconclusive transport result, or a success response without a non-negative deleted count, returns `outcome_unknown`, and the caller inspects `queue list` before trying again. A conclusive InvokeAI rejection returns `invokeai_operation_failed`.

Read-only inspection results are normalized Bediz values rather than passthrough InvokeAI response documents. This keeps the V1 JSON shape stable and prevents backend-only or sensitive fields from becoming part of the public contract.

### 15.2 Board inspection and creation

`boards list` accepts `offset` (default zero), `limit` (default twenty), and `include_archived` (default false). Limits below one or above one hundred and a negative offset are invalid local requests and return exit status 2 before any network request. Results keep InvokeAI's order, newest first by creation time. InvokeAI 6.14.1 applies no tiebreaker before paging, so Bediz promises no order among boards with equal creation times and does not re-sort a page. The result carries the requested page, the offset and limit, and InvokeAI's reported total.

A board summary contains only `board_id`, `board_name`, `image_count`, `archived`, an optional `cover_image_name`, and the `created_at` and `updated_at` timestamps as InvokeAI reports them. Owner, visibility, video, asset, and deletion fields are not exposed.

`boards get SELECTOR`, or a Request Document with a required non-empty `board`, first tries the selector as an exact board identifier. If no visible board has that identifier, Bediz reads every visible board, archived ones included, and matches the exact, case-sensitive name. A single match wins. Several matches return `selection_required` with `kind: "board"`, the selector, and candidates carrying `board_id` and `board_name`, sorted by board identifier. No match returns `not_found` with exit status 6. The result is `{"board": <board summary>}`.

InvokeAI 6.14.1 shows an admin every board. It shows any other user their own boards, boards shared with them, and boards with `shared` or `public` visibility, including those owned by other users. Bediz reports that scope as is. The board detail route answers 403 for another user's private board; Bediz treats that like an absent identifier, so name lookup and `not_found` cover only visible boards. Both operations are read-only inspection and may run on an untested but compatible InvokeAI version.

`boards create NAME`, or a Request Document `{"schema_version": 1, "board_name": "<name>"}`, creates one board. The name is sent exactly as given; a name that is empty after trimming whitespace is an invalid local request and returns exit status 2 before any network request. Creation requires an InvokeAI version in the supported range. Before the mutation, Bediz reads every visible board, archived ones included, and when any has exactly the same case-sensitive name it returns `invalid_request` with `reason: "board_name_exists"` and `board_ids`, every matching board identifier sorted ascending, without sending the mutation. The check covers exactly the boards the caller can see, whoever owns them; a board the caller cannot see does not block creation. InvokeAI itself allows duplicate names, so boards created by other clients can still share a name, and `boards get` reports those through `selection_required`. The create request is sent once and never retried. An inconclusive transport result, or a success response without a board identifier, returns `outcome_unknown`, and the caller inspects `boards list` before trying again. A conclusive InvokeAI rejection returns `invokeai_operation_failed`. The result is `{"board": <board summary>}`.

### 15.3 Inspection safety

List results contain no more than the requested page. For queue listing against the supported InvokeAI 6.14.x API, Bediz first retrieves the complete lightweight, ordered item-ID index because that endpoint does not support pagination. This index response may grow with the queue and is constrained by the configured HTTP response-size limit. Bediz then selects the requested offset and limit from the index, hydrates only those IDs through the lightweight summary endpoint, preserves the index ordering and reported total count, and never fetches queue-item execution graphs. Summary hydration and public output are therefore page-bounded even though retrieval of the backend ID index is not. `images download` streams the full image to a local file instead of buffering it, under its own 256 MiB limit (§15.1). Name lookup in `boards get` and the duplicate-name check in `boards create` likewise read InvokeAI's complete visible board list, because InvokeAI 6.14.x offers no name filter; that response is constrained by the same limit, and only the resolved board or the candidate identifiers and names are returned.

Read-only requests may use a GET or a semantically read-only POST endpoint. Retry safety is determined by operation semantics, not only by the HTTP method. Transient read failures may be retried within the configured limit.

Image upload and deletion, board creation, queue cancellation, and queue clearing are mutations under §17.

## 16. Profiles

`bediz profiles create --request PATH|-`, `profiles list`, `profiles get NAME`, and `profiles delete NAME --yes` operate only on the CLI machine. They make no InvokeAI request. Profiles are JSON files at `<user configuration directory>/bediz/profiles/<name>.json`, next to `config.json`. V1 has no project-local or cloud profile lookup. Names match `^[a-z0-9][a-z0-9_-]{0,63}$`; every command validates a supplied name before constructing a path.

The Profile Document has `schema_version: 1`, a `name` matching its filename, and at least one of `generate` or `upscale` (an empty section is allowed). `generate` accepts optional `model`, `components` (`vae`, `qwen3_encoder`, `t5_encoder`, `clip_embed`), paired `width` and `height`, `steps`, `scheduler`, `guidance`, and `output_count`. `upscale` accepts optional `model`, `components` (`upscale_model`, `tile_controlnet`, `vae`), `scale`, `creativity`, `structure`, `steps`, `scheduler`, `guidance`, `tile_size`, and `tile_overlap`. Profile Documents follow the §8.1 strict object rules at every depth. Prompts, seeds, source images, output boards, tokens, and other secrets are unknown fields and cannot be stored.

Create validates only family-independent rules: non-empty model and component selectors; positive steps and output count; positive paired dimensions; finite guidance of at least 1; a scheduler from any registered generation family's list; and the §13.1 upscale bounds for scale, creativity, structure, tile size, and tile overlap. Family applicability is validated when a profile is used. Create stores the validated document without adding defaults. `profiles get` returns the stored document in the V1 Result Envelope's `data`. `profiles list` returns `{"profiles":[{"name":"...","sections":["generate","upscale"]}]}` in `data`, sorted by name; it ignores files whose names do not match the rule. A malformed stored profile returns `invalid_configuration` naming that profile.

Creating an existing name returns `invalid_request` with `details.reason: "profile_exists"` unless both `--replace` and `--yes` are supplied. `--replace` without `--yes` is an invalid request. Replacement writes a temporary file and atomically renames it into place, leaving the old profile intact if the write fails. `profiles delete` requires `--yes` and removes only the named profile. A missing profile on get or delete returns `not_found`; a local write or removal failure returns `configuration_write_failed`. Bediz retains no profile revision history; schema versioning does not mean historical revisions.

## 17. Retry, timeout, and uncertain outcomes

Bediz may retry safe read-only requests a limited number of times after transient failures. It never automatically retries enqueue, upload, install, create, delete, cancel, clear, or other mutations.

If a connection fails after InvokeAI may have accepted a mutation, Bediz returns `outcome_unknown` with exit status 6. The caller inspects the relevant queue, model, board, or image state before deciding whether to submit another request.

A 502, 503, or 504 answer to a mutation is also `outcome_unknown`, with the status in `details.status`, because it comes from an intermediary that may already have forwarded the request (ADR-0020). Every other non-2xx answer to a mutation is a conclusive rejection. A safe read may retry these gateway statuses within its limit.

Bediz never follows a redirect for a mutation. Following one would resend the request, or turn it into a GET after 301, 302, or 303 and report that GET's answer as the mutation's. A redirect answer is a conclusive `invokeai_operation_failed` with the redirect status in `details.status`, and the caller corrects the configured InvokeAI URL. Safe reads follow redirects.

Ordinary connection and HTTP calls have bounded timeouts. Generation and queue waiting have no total timeout unless `--timeout` is supplied. An elapsed wait deadline returns `wait_timeout` and never cancels the remote item.

## 18. Approval and destructive operations

Generation, upscale, image upload and download, enqueue, waiting, and queue cancellation require no additional CLI approval.

Delete, bulk-clear, profile replacement, and moving model files require Execution Approval, an explicit `--yes`, as specified by their commands. `--yes` is never a Request Document field and is required even when the request comes from a document.

The agent skill may install a model without another confirmation when the user explicitly requested that model be installed or used. When a normal creative request merely reveals a missing model, the skill first reports the source, approximate size, and known license information and obtains installation consent. It prefers compatible installed models when possible.

## 19. Agent skill

The repository ships one canonical `skills/bediz/SKILL.md`. It teaches a creative agent to:

- Run readiness checks when capability state is unknown.
- Inspect installed models and resolve exact identifiers.
- Translate user intent into typed Bediz requests.
- Use `--json` and structured errors.
- Improve unspecified prompts and settings without overriding explicit constraints.
- Handle `selection_required`, `outcome_unknown`, and synchronization warnings safely.
- Use browser research for discovery while leaving deterministic installation and execution to Bediz.
- Obtain installation consent when required.

The skill contains no graph-building logic or private InvokeAI payload construction. Other agent systems may use thin adapters derived from the canonical skill.

The Agent Skill uses the Agent Skills format. The `skills/bediz/` directory holds `SKILL.md` and the reference files it links. The `SKILL.md` frontmatter carries `name: bediz`, a trigger-oriented `description`, and `metadata.bediz-version`, the `vX.Y.Z` Bediz version the skill matches, which an agent compares with `bediz version`. Before each release tag, `metadata.bediz-version` is set to that tag's version. A test runs every `bediz` command path and long flag the skill shows against the CLI's own help and fails when the CLI no longer accepts one.

The install scripts install the skill from the tag of the binary they install (section 21). `npx skills add avienor/bediz` installs the skill from the default branch. To match an installed binary, install the skill from that binary's tag:

```text
npx skills add https://github.com/avienor/bediz/tree/<tag>/skills/bediz
```

The tree form installs the files from the named tag, not from the default branch. Add `-g` to install the skill for the user instead of the current project.

## 20. Security and licensing

Bediz is licensed under Apache License 2.0. Adapted upstream material retains required copyright and notice information.

Bediz does not log tokens or include secrets in profiles, receipts, results, or diagnostics. It does not weaken InvokeAI authentication or verification. Bediz redacts installation request URLs and projects only safe backend job fields; InvokeAI's own temporary install markers and any upstream access logs are governed by the source-token boundary in §14.7. When InvokeAI has a stored Hugging Face login, its 6.14.1 installer attaches that token to starter subfolder downloads from public as well as protected repositories and can write it to a plaintext temporary install marker. Normal completion removes the marker; a paused or interrupted job can retain it. Bediz neither reads nor transmits the stored login token, including in its anonymous preflight requests. Model licenses remain distinct from the Bediz software license; the agent reports known source license information before an inferred installation but Bediz does not invent or guarantee missing license metadata.

## 21. Release targets

Initial release artifacts are:

- Linux amd64
- Windows amd64
- macOS arm64
- one `SHA256SUMS` checksum file
- `go install` support

A release for version `vX.Y.Z` or `vX.Y.Z-<prerelease>` is one directory holding:

| File | Contents |
| --- | --- |
| `bediz_<version>_linux_amd64.tar.gz` | `bediz`, `LICENSE`, `README.md` |
| `bediz_<version>_darwin_arm64.tar.gz` | `bediz`, `LICENSE`, `README.md` |
| `bediz_<version>_windows_amd64.zip` | `bediz.exe`, `LICENSE`, `README.md` |
| `SHA256SUMS` | One `<sha256>  <archive name>` line per archive, sorted by name, readable by `sha256sum -c` |

The archives hold exactly these files, in this order, at the archive root. Every entry carries the tagged commit time. Zip entries store it in MS-DOS format, which has two-second precision, so an odd-second commit time is stored one second earlier. The agent skill is not bundled. The repository-local release command builds them reproducibly from the version's tag (ADR-0021). Two builds of the same tag with the Go toolchain pinned in `go.mod` produce byte-identical archives.

The release command also refuses a version that differs from the skill's `metadata.bediz-version` (section 19). Pushing a `v*` tag publishes that tag: a workflow runs the verification commands with the pinned toolchain, builds the release directory with the same command, and uploads its archives and `SHA256SUMS` as a GitHub Release for the tag. A version with a prerelease suffix is published as a prerelease. A failed check, verification, or build publishes nothing, and an existing release is never replaced.

`bediz version`, `bediz version --json`, and the `bediz` section of `doctor` report the same `version`, `commit`, and `date` fields. Bediz takes the values from the first available source:

1. A release build reports the version, commit, and UTC commit date injected at build time.
2. Otherwise the Go build information supplies the main module version and the VCS revision and time. A `go install github.com/avienor/bediz/cmd/bediz@vX.Y.Z` build reports `vX.Y.Z`. The Go module cache carries no VCS data, so that build omits `commit` and `date`. The `(devel)` module version is treated as absent.
3. A build without either source reports version `dev`. It omits `commit` and `date` instead of reporting placeholder values.

The supported installation paths are:

- The install scripts `install.sh` (Linux amd64 and macOS arm64) and `install.ps1` (Windows amd64) at the repository root, run from the default branch.
- A release archive from the GitHub Release, verified against its `SHA256SUMS`, with the binary placed in a user-owned directory on `PATH`.
- `go install github.com/avienor/bediz/cmd/bediz@latest`, or `@vX.Y.Z` for a named version.

An install script installs the latest non-prerelease release, or the tag in `BEDIZ_VERSION`. It refuses an unsupported platform with the supported list, and fails when no non-prerelease release exists and no tag is named. It downloads the matching archive and `SHA256SUMS`, and installs nothing when the archive has no checksum line or its checksum differs. It copies the binary to `BEDIZ_INSTALL_DIR`, by default `~/.local/bin` or `%LOCALAPPDATA%\Programs\bediz` on Windows, and fails when the installed binary does not report the tag. It never uses elevated rights or changes `PATH` or shell profiles; it reports when the directory is not on `PATH` or another `bediz` comes first.

When `npx` and an interactive terminal are available, the script opens the skill installer's own agent selection with `npx -y skills add <tree URL> -g`, using the same tag as the binary. The leading `npx -y` accepts running the npm package; the skill command receives no `--yes`, so its native agent selection and confirmation remain interactive. On Linux and macOS, the script gives the skill installer terminal input through `/dev/tty` even when the script itself arrives through `curl | sh`. When Node.js or an interactive terminal is unavailable, or the skill installer fails, the script prints `npx skills add <tree URL> -g` to run later and still succeeds after installing the binary. Cancelling skill installation leaves the binary installed; the script relays the skill installer's result without claiming that a zero exit status proves a skill was installed.

The README documents these paths for people. `INSTALLATION.md` at the repository root instructs an agent to run the install script, to ask before changing `PATH`, to relay the script's other notes, and to end with a `bediz doctor --json` summary. The agent never handles InvokeAI or Hugging Face tokens. The Bediz binary has no command that installs itself or the skill.

Package-manager formulas, a self-updater, additional architectures, and signed installers are deferred.

## 22. Verification strategy

The graph compiler and request resolution are pure and covered by unit tests. Each advertised family has versioned graph fixtures and validation tests. API behavior is tested against the InvokeAI 6.14.1 OpenAPI contract, and meaningful end-to-end tests run against a live local InvokeAI instance.

Compatibility tests verify that unsupported fields and versions fail explicitly, component ambiguity returns candidates, JSON standard output remains parseable, unsafe mutations are not retried, and Recall failures become warnings without changing successful generation outcomes.

## 23. Delivery sequence

V1 was delivered in vertical slices, as ADR-0015 records, and released as v1.0.0. Later changes follow the versioning rules in §25.

## 24. V1 acceptance

V1 is accepted when all advertised commands and family combinations pass their tests on the supported InvokeAI range, unsupported combinations fail explicitly, the capability matrix and `doctor` agree, the JSON contract is stable, the canonical skill can complete an end-to-end generation through Bediz, and the documented release artifacts are reproducible.

## 25. Versioning after V1

This document is the contract for schema version 1 and stays current after v1.0.0. A change that keeps schema version 1 is recorded here when it is accepted, and each release lists its changes in `CHANGELOG.md`.

Within schema version 1, changes are additive. A release may add a command, flag, model family, capability, supported InvokeAI range, optional Request Document field, Result Envelope data field, warning, or error code for a situation that had none. Callers ignore Result Envelope fields they do not know; Request Documents remain strict (§8.1).

A breaking change requires schema version 2 and a new `docs/spec/v2.md`. Breaking changes include removing or renaming a command, flag, request field, or result field; changing a field's type or meaning; making an optional field required; changing a documented default, the error code or exit status for an existing situation, or the retry and approval rules of §17 and §18.

Bediz release versions follow semantic versioning: a patch release fixes behavior to match this document, a minor release adds behavior under the rules above, and a major release accompanies a new schema version. Schema version and Bediz release version are separate numbers (see Schema Version in `CONTEXT.md`).
